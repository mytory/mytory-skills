`HEAD`와 사용자가 지정한 기준점 사이의 차이를 두 축으로 검토합니다.

- **표준**: 저장소에 문서화된 코딩 표준을 따르는가?
- **명세**: 원본 이슈나 명세의 요구사항을 충실히 구현했는가?

두 축은 **병렬 하위 에이전트**가 독립적으로 검토한 뒤 결과를 합칩니다. 이슈 트래커 설정이 없다면 사용자에게 `/setup-matt-pocock-skills`를 실행하도록 안내합니다.

## 절차

### 1. 기준점 확정

사용자가 지정한 커밋 SHA, 브랜치, 태그, `main`, `HEAD~5` 등을 기준점으로 사용합니다. 지정하지 않았다면 질문합니다.

비교 명령은 `git diff <fixed-point>...HEAD`입니다. 세 점은 merge-base를 기준으로 비교합니다. `git log <fixed-point>..HEAD --oneline`으로 커밋 목록도 확인합니다. `git rev-parse <fixed-point>`로 참조를 검증하고 diff가 비어 있지 않은지 확인한 뒤 다음 단계로 갑니다.

### 2. 명세 출처 찾기

다음 순서로 찾습니다.

1. 커밋 메시지의 이슈 참조(`#123`, `Closes #45`, GitLab `!67` 등). 트래커 문서의 절차로 가져옵니다.
2. 사용자가 인수로 전달한 경로.
3. 브랜치 이름이나 기능과 맞는 `docs/`, `specs/`, `.scratch/`의 명세 파일.
4. 찾지 못하면 사용자에게 위치를 묻습니다. 명세가 없다고 하면 명세 검토를 건너뛰고 "명세 없음"으로 보고합니다.

### 3. 표준 출처 찾기

코드 작성 방식을 문서화한 파일을 모두 찾습니다. `CODING_STANDARDS.md` 또는 `CONTRIBUTING.md`가 있으면 반드시 포함합니다.

저장소 문서와 별개로 아래 Fowler 코드 냄새(_Refactoring_ 3장)를 기본 점검 기준으로 사용합니다. 저장소의 명시적 표준이 우선하며, 냄새에 해당해도 저장소가 허용한다면 보고하지 않습니다. 각 냄새는 확정 위반이 아닌 **판단이 필요한 가능성**으로 표시합니다. 도구가 이미 강제하는 항목은 건너뜁니다.

- **모호한 이름(Mysterious Name)**: 함수, 변수, 타입 이름이 역할을 드러내지 않음 → 정확히 이름을 바꿉니다. 적절한 이름이 없으면 설계를 살핍니다.
- **중복 코드(Duplicated Code)**: 같은 로직 형태가 여러 변경 부분에 나타남 → 공통 부분을 추출합니다.
- **다른 객체의 데이터에 치우침(Feature Envy)**: 메서드가 자신의 데이터보다 다른 객체의 데이터를 더 많이 사용함 → 해당 데이터가 있는 객체로 옮깁니다.
- **뭉쳐 다니는 데이터(Data Clumps)**: 같은 필드나 매개변수가 늘 함께 전달됨 → 하나의 타입으로 묶습니다.
- **기본형 집착(Primitive Obsession)**: 도메인 개념을 원시값이나 문자열로 표현함 → 작은 전용 타입을 만듭니다.
- **반복되는 분기(Repeated Switches)**: 같은 타입에 대한 `switch`나 `if` 연쇄가 반복됨 → 다형성이나 공통 맵을 사용합니다.
- **산탄총 수술(Shotgun Surgery)**: 한 논리적 변경 때문에 여러 파일을 흩어져 수정함 → 함께 바뀌는 코드를 한 모듈에 모읍니다.
- **발산적 변경(Divergent Change)**: 한 파일이 서로 무관한 이유로 여러 번 수정됨 → 변경 이유별로 나눕니다.
- **추측성 일반화(Speculative Generality)**: 명세에 없는 미래 수요를 위한 추상화, 매개변수, 훅 → 실제 필요가 생길 때까지 제거합니다.
- **메시지 사슬(Message Chains)**: 호출자가 몰라도 될 긴 `a.b().c().d()` 탐색 → 첫 객체의 메서드 뒤에 숨깁니다.
- **중개인(Middle Man)**: 대부분 다른 대상으로 전달만 하는 클래스나 함수 → 제거하고 실제 대상을 호출합니다.
- **거부된 유산(Refused Bequest)**: 상속받은 기능 대부분을 무시하거나 재정의하는 하위 타입 → 상속 대신 합성을 사용합니다.

### 4. 두 하위 에이전트를 병렬 실행

두 요청을 함께 실행하고 반환된 보고서를 취합합니다.

**표준 검토 에이전트**에게 diff 명령, 커밋 목록, 표준 파일 목록, 위 코드 냄새 목록 전체를 전달합니다. 파일과 변경 부분별로 (a) 문서화된 표준 위반과 해당 문서·규칙, (b) 발견한 코드 냄새의 이름과 변경 부분을 보고하도록 요청합니다. 명시적 위반과 판단이 필요한 냄새를 구분하고, 저장소 표준이 우선하며, 도구가 강제하는 항목은 건너뛰도록 합니다. 400단어 이내로 제한합니다.

**명세 검토 에이전트**에게 diff 명령, 커밋 목록, 명세 경로나 내용을 전달합니다. (a) 빠졌거나 일부만 구현된 요구사항, (b) 요청하지 않은 동작, (c) 구현은 있어 보이지만 잘못된 요구사항을 보고하도록 요청합니다. 각 발견에 명세의 해당 줄을 인용하게 합니다. 400단어 이내로 제한합니다.

명세가 없다면 명세 검토 에이전트를 생략하고 최종 보고에 적습니다.

### 5. 결과 취합

두 보고서를 `## Standards`와 `## Spec` 아래에 그대로 또는 가볍게 정리해 제시합니다. 발견 사항을 합치거나 우선순위를 다시 매기지 않습니다. 마지막에 축별 발견 개수와 각 축에서 가장 심각한 문제를 한 줄로 요약합니다. 두 축 사이의 단일 우승 문제를 고르지 않습니다.

## 두 축으로 나누는 이유

코딩 표준을 모두 따르면서 요구사항을 잘못 구현할 수 있고, 요구사항대로 동작하면서 저장소 관례를 어길 수도 있습니다. 따로 보고해야 한쪽의 결과가 다른 쪽을 가리지 않습니다.
