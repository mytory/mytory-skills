# 테스트 주도 개발

TDD는 빨강 → 초록의 반복입니다. 이 스킬은 그 반복에서 유지할 가치가 있는 테스트를 만드는 기준을 제공합니다. 좋은 테스트의 조건, 테스트를 둘 경계, 안티패턴, 반복 규칙을 매 주기 전과 도중에 확인합니다.

코드베이스를 탐색할 때 `GLOSSARY.md`가 있으면 읽고, 테스트 이름과 인터페이스 용어를 프로젝트 도메인에 맞춥니다. 수정하는 영역의 ADR도 따릅니다.

## 좋은 테스트

테스트는 구현 세부사항이 아닌 공개 인터페이스를 통한 동작을 검증합니다. 코드를 완전히 바꿔도 동작이 같다면 테스트는 유지되어야 합니다. 좋은 테스트는 명세처럼 읽힙니다. "유효한 장바구니로 결제할 수 있다"는 기능을 정확히 설명하며 내부 구조에 의존하지 않으므로 리팩터링에도 유지됩니다.

예시는 [tests.md](tests.md), 모킹 지침은 [mocking.md](mocking.md)를 참고합니다.

## 경계: 테스트 위치

**경계(seam)**는 내부를 들여다보지 않고 동작을 관찰하는 공개 인터페이스입니다. 테스트는 내부 구현이 아닌 경계에 둡니다.

**사전에 합의한 경계만 테스트합니다.** 테스트를 작성하기 전에 대상 경계를 적고 사용자에게 확인받습니다. 확인하지 않은 경계에는 테스트를 작성하지 않습니다. 각 경계가 포착하는 문제와 놓치는 문제를 한 줄씩 설명합니다. 모든 것을 테스트할 수 없으므로 핵심 경로와 복잡한 로직에 집중합니다.

질문: "공개 인터페이스는 무엇이며, 어떤 경계를 테스트해야 하나요?"

인터페이스의 형태 자체가 불분명하다면 Skill 도구로 `codebase-design`을 참고합니다. 그 스킬은 모듈, 인터페이스, 깊이, 경계, 어댑터, 활용도, 지역성에 관한 공통 용어를 제공하는 참고 자료입니다.

## 안티패턴

- **구현 결합**: 내부 협력자를 모킹하거나 비공개 메서드를 테스트하거나, 인터페이스 대신 DB를 직접 조회하는 등 다른 경로로 검증합니다. 동작이 그대로인데 리팩터링 후 테스트가 깨진다면 경고 신호입니다.
- **동어반복**: `expect(add(a, b)).toBe(a + b)`처럼 구현과 같은 방식으로 기대값을 다시 계산하거나, 같은 방식으로 직접 만든 스냅샷 또는 상수를 자기 자신과 비교합니다. 기대값은 알려진 정답, 계산이 완료된 예시, 명세 등 독립적인 근거에서 가져와야 합니다.
- **수평 분할**: 모든 테스트를 먼저 쓰고 모든 구현을 나중에 합니다. 이 방식은 실제 동작보다 상상한 형태를 테스트하게 하고, 구현을 이해하기 전에 테스트 구조를 고정합니다. 대신 테스트 하나 → 구현 하나를 반복하는 **수직 분할**을 사용합니다. 각 테스트는 이전 주기에서 배운 내용에 반응하는 **탐색용 한 걸음(tracer bullet)**이어야 합니다.

## 반복 규칙

- **초록보다 빨강이 먼저입니다.** 먼저 실패하는 테스트를 작성하고, 통과에 필요한 최소한의 코드만 작성합니다. 미래의 테스트나 기능을 미리 구현하지 않습니다.
- **한 번에 하나의 조각만 다룹니다.** 한 경계, 한 테스트, 최소 구현 하나로 한 주기를 구성합니다.
- **리팩터링은 이 반복의 일부가 아닙니다.** 리팩터링은 검토 단계에서 수행합니다(`code-review` 스킬 참고).
