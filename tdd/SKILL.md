# 테스트 주도 개발

## 철학

**핵심 원칙**: 테스트는 구현 세부사항이 아닌 공개 인터페이스를 통해 동작을 검증해야 합니다. 코드는 완전히 바뀔 수 있지만 테스트는 바뀌지 않아야 합니다.

**좋은 테스트**는 통합 스타일: 공개 API를 통해 실제 코드 경로를 실행합니다. 시스템이 _무엇을_ 하는지 설명하고, _어떻게_ 하는지 설명하지 않습니다. 좋은 테스트는 명세처럼 읽힙니다 — "유효한 장바구니로 체크아웃할 수 있다"는 어떤 기능이 존재하는지 정확히 알려줍니다. 이러한 테스트는 내부 구조에 신경 쓰지 않기 때문에 리팩터링에서 살아남습니다.

**나쁜 테스트**는 구현에 결합됩니다. 내부 협력자를 모킹하고, 비공개 메서드를 테스트하거나, 외부 수단을 통해 검증합니다(인터페이스를 사용하는 대신 데이터베이스를 직접 쿼리하는 등). 경고 신호: 리팩터링할 때 테스트가 깨지는데, 동작은 변경되지 않음. 내부 함수 이름을 바꿨는데 테스트가 실패하면, 그 테스트는 동작이 아닌 구현을 테스트하고 있었던 것입니다.

예시는 [tests.md](tests.md), 모킹 가이드라인은 [mocking.md](mocking.md) 참조.

## 안티패턴: 수평 슬라이스

**모든 테스트를 먼저 작성한 후 모든 구현을 하지 마세요.** 이것이 "수평 슬라이싱" — RED를 "모든 테스트 작성"으로, GREEN을 "모든 코드 작성"으로 취급하는 것.

이것은 **형편없는 테스트**를 만듭니다:

- 대량으로 작성된 테스트는 _실제_ 동작이 아닌 _상상된_ 동작을 테스트
- 사용자 대상 동작이 아닌 것들의 _형태_(데이터 구조, 함수 시그니처)를 테스트하게 됨
- 테스트가 실제 변경에 둔감해짐 — 동작이 깨져도 통과하고, 동작이 정상이어도 실패
- 구현을 이해하기 전에 테스트 구조에 커밋하게 되어 헤드라이트를 넘어서 달리게 됨

**올바른 접근법**: 트레이서 불릿을 통한 수직 슬라이스. 테스트 하나 → 구현 하나 → 반복. 각 테스트는 이전 주기에서 배운 것에 응답합니다. 방금 코드를 작성했기 때문에 어떤 동작이 중요한지, 어떻게 검증할지 정확히 압니다.

```
틀림 (수평):
  RED:   test1, test2, test3, test4, test5
  GREEN: impl1, impl2, impl3, impl4, impl5

맞음 (수직):
  RED→GREEN: test1→impl1
  RED→GREEN: test2→impl2
  RED→GREEN: test3→impl3
  ...
```

## 작업 흐름

### 1. 계획

코드베이스 탐색 시, 프로젝트의 도메인 용어집을 사용하여 테스트명과 인터페이스 어휘가 프로젝트 언어와 일치하게 하고, 다루는 영역의 ADR을 존중.

코드 작성 전:

- [ ] 필요한 인터페이스 변경을 사용자와 확인
- [ ] 어떤 동작을 테스트할지 확인 (우선순위)
- [ ] [깊은 모듈](deep-modules.md) 기회 식별 (작은 인터페이스, 깊은 구현)
- [ ] [테스트 가능성](interface-design.md)을 위한 인터페이스 설계
- [ ] 테스트할 동작 목록 (구현 단계가 아닌)
- [ ] 계획에 대한 사용자 승인 받기

질문: "공개 인터페이스는 어떻게 생겨야 하나요? 어떤 동작을 테스트하는 게 가장 중요한가요?"

**모든 것을 테스트할 수는 없습니다.** 정확히 어떤 동작이 가장 중요한지 사용자와 확인. 테스트 노력을 중요한 경로와 복잡한 로직에 집중하고, 가능한 모든 엣지 케이스가 아님.

### 2. 트레이서 불릿

시스템에 대해 한 가지를 확인하는 하나의 테스트 작성:

```
RED:   첫 번째 동작에 대한 테스트 작성 → 테스트 실패
GREEN: 통과할 최소 코드 작성 → 테스트 통과
```

이것이 당신의 트레이서 불릿 — 경로가 끝에서 끝까지 작동함을 증명.

### 3. 점진적 루프

남은 각 동작에 대해:

```
RED:   다음 테스트 작성 → 실패
GREEN: 통과할 최소 코드 → 통과
```

규칙:

- 한 번에 하나의 테스트
- 현재 테스트를 통과할 만큼만 코드
- 미래 테스트 예상하지 않기
- 테스트를 관찰 가능한 동작에 집중

### 4. 리팩터

모든 테스트 통과 후, [리팩터 후보](refactoring.md) 찾기:

- [ ] 중복 추출
- [ ] 모듈 깊이화 (복잡성을 단순한 인터페이스 뒤로 이동)
- [ ] 자연스러운 곳에 SOLID 원칙 적용
- [ ] 새 코드가 기존 코드에 대해 드러내는 것 고려
- [ ] 각 리팩터 단계 후 테스트 실행

**절대 RED 상태에서 리팩터하지 마세요.** 먼저 GREEN으로.

## 주기별 체크리스트

```
[ ] 테스트가 구현이 아닌 동작을 설명
[ ] 테스트가 공개 인터페이스만 사용
[ ] 테스트가 내부 리팩터에서 살아남을 것
[ ] 코드가 이 테스트에 최소한
[ ] 추측적 기능 추가 없음
```
