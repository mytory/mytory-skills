# 이슈 분류

프로젝트 이슈 트래커의 이슈를 작은 분류 상태 머신에 따라 이동합니다.

이 저장소에서 외부 PR도 요청을 받는 통로라면(이슈 트래커 설정 참고), PR도 분류합니다. **PR은 코드가 첨부된 이슈**로 취급하고 아래에서 "PR의 경우"라고 표시한 차이점만 적용합니다. 단독으로 주어진 `#42`가 이슈인지 PR인지는 트래커 설정에 따라 해석합니다.

분류 중 이슈 트래커에 올리는 모든 댓글과 이슈는 **반드시** 다음 문구로 시작합니다.

```
> *This was generated by AI during triage.*
```

## 참고 문서

- [AGENT-BRIEF.md](AGENT-BRIEF.md): 오래 사용할 수 있는 에이전트 작업 지시서 작성법
- [OUT-OF-SCOPE.md](OUT-OF-SCOPE.md): `.out-of-scope/` 지식 저장소 사용법

## 역할

**분류** 역할 두 가지:

- `bug`: 기능이 고장남
- `enhancement`: 새 기능 또는 개선

**상태** 역할 다섯 가지:

- `needs-triage`: 관리자의 평가 필요
- `needs-info`: 제보자의 추가 정보 대기
- `ready-for-agent`: 명세가 충분해 에이전트가 작업 가능
- `ready-for-human`: 사람이 구현해야 함
- `wontfix`: 작업하지 않음

PR에서는 첨부된 코드에 이 상태를 적용합니다. `ready-for-agent`는 작업 지시서가 첨부돼 에이전트가 diff에서 다음 작업을 해야 한다는 뜻입니다. `ready-for-human`은 사람이 병합할 준비가 되었다는 뜻입니다.

분류된 항목에는 분류 역할 하나와 상태 역할 하나가 정확히 있어야 합니다. 상태 역할이 충돌하면 다른 작업 전에 관리자에게 알리고 질문합니다.

위 이름은 표준 역할 이름입니다. 트래커의 실제 라벨 이름은 다를 수 있습니다. 매핑이 없다면 사용자에게 `/setup-matt-pocock-skills`를 실행하도록 안내합니다.

라벨이 없는 이슈는 보통 먼저 `needs-triage`가 됩니다. 그다음 `needs-info`, `ready-for-agent`, `ready-for-human`, `wontfix`로 이동합니다. `needs-info`는 제보자가 답하면 `needs-triage`로 돌아옵니다. 관리자는 언제든 상태를 바꿀 수 있습니다. 이례적인 전환이라면 먼저 알리고 질문합니다.

## 호출

관리자는 `/triage`와 함께 원하는 작업을 자연어로 설명합니다. 요청을 해석하고 수행합니다. 예:

- "내가 확인할 항목을 보여줘"
- "#42를 살펴보자" (이슈 또는 PR)
- "#42를 ready-for-agent로 이동해줘"
- "에이전트가 맡을 준비가 된 항목은?"

## 확인이 필요한 항목 보여주기

트래커를 조회해 다음 세 묶음을 오래된 순서대로 보여줍니다.

1. **라벨 없음**: 아직 분류하지 않음
2. **`needs-triage`**: 평가 진행 중
3. **최근 제보자가 활동한 `needs-info`**: 마지막 분류 기록 이후 활동이 있어 재평가 필요

PR이 범위에 포함되면 외부 PR도 포함하고 각 줄에 `[PR]` 또는 `[issue]`를 표시합니다. 외부 PR의 기준은 트래커 설정을 따릅니다. 발견 단계에서만 외부 PR로 한정합니다. 명시적으로 지목된 PR은 작성자와 관계없이 분류합니다.

항목별 개수와 한 줄 요약을 보여주고 관리자가 선택하게 합니다.

## 특정 이슈 또는 PR 분류

1. **맥락 수집.** 본문, 댓글, 라벨, 작성자, 날짜를 모두 읽습니다. PR이면 diff도 읽습니다. 이전 분류 기록을 확인해 해결된 질문을 다시 묻지 않습니다. 프로젝트 용어집과 해당 영역의 ADR을 참고해 코드를 탐색합니다. 두 가지를 확인합니다. (a) **중복**: 요청 문구뿐 아니라 도메인 개념으로 기존 구현을 찾아보고 검색 범위를 보고합니다. 이미 구현됐다면 5단계의 `wontfix`로 갑니다. (b) **이전 거절**: `.out-of-scope/*.md`에서 유사한 요청을 찾습니다.
2. **권고.** 분류와 상태를 이유와 함께 제안합니다. 이미 구현됐는지 포함해 관련 코드의 간단한 요약을 전달하고 관리자의 지시를 기다립니다.
3. **주장 검증.** 추가 질문 전에 내용을 확인합니다. 버그는 제보된 절차로 재현합니다. PR은 체크아웃하여 관련 테스트나 명령을 실행하고 diff가 주장대로 동작하는지 확인합니다. 코드 경로와 함께 확인됨, 실패, 정보 부족 중 하나로 결과를 보고합니다.
4. **필요하면 질문.** 요청이 구체화되어야 한다면 Skill 도구에서 `grilling`과 `domain-modeling`을 각각 호출합니다. 한 번에 한 묶음씩 질문하고, 결정이 내려지는 대로 도메인 용어와 `GLOSSARY.md`/ADR을 갱신합니다.
5. **결과 적용.**
   - `ready-for-agent`: [AGENT-BRIEF.md](AGENT-BRIEF.md)에 따라 작업 지시서 댓글을 게시합니다.
   - `ready-for-human`: 같은 형식을 쓰되 위임할 수 없는 이유(판단, 외부 접근, 설계 결정, 수동 테스트)를 적습니다.
   - `needs-info`: 아래 양식으로 분류 기록을 게시합니다.
   - `wontfix`: 이유에 따라 댓글을 남기고 닫습니다. 이미 구현된 경우 위치를 안내하고 `.out-of-scope/`에는 기록하지 않습니다. 거절한 버그는 정중하게 설명합니다. 거절한 개선 요청은 `.out-of-scope/`에 기록하고 댓글에서 연결합니다([OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)).
   - `needs-triage`: 역할을 적용합니다. 일부 진전이 있다면 선택적으로 댓글을 남깁니다.

## 빠른 상태 변경

관리자가 "#42를 ready-for-agent로 옮겨줘"라고 하면 판단을 신뢰하고 역할을 바로 적용합니다. 바꾸려는 역할과 댓글 게시 또는 닫기 여부를 확인한 뒤 수행합니다. 추가 질문 과정은 건너뜁니다. 사전 질문 과정 없이 `ready-for-agent`로 옮길 때는 작업 지시서도 작성할지 묻습니다.

## 추가 정보 요청 양식

```markdown
## 분류 기록

**지금까지 확인한 내용:**

- 항목 1
- 항목 2

**제보자(@reporter)에게 필요한 내용:**

- 질문 1
- 질문 2
```

질문 과정에서 해결한 내용을 모두 "지금까지 확인한 내용"에 기록합니다. 질문은 "정보를 더 주세요"가 아니라 구체적으로 답할 수 있어야 합니다.

## 이전 세션 이어가기

이슈나 PR에 이전 분류 기록이 있다면 읽고, 제보자가 남은 질문에 답했는지 확인합니다. 이어서 작업하기 전에 현재 상황을 정리합니다. 해결된 질문을 다시 묻지 않습니다.
