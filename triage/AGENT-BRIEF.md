# 에이전트 브리프 작성

에이전트 브리프는 이슈가 `ready-for-agent`로 이동할 때 GitHub 이슈에 게시되는 구조화된 코멘트입니다. AFK 에이전트가 작업할 권위 있는 명세입니다. 원본 이슈 본문과 논의는 컨텍스트입니다 — 에이전트 브리프가 계약입니다.

## 원칙

### 정밀성보다 내구성

이슈는 며칠 또는 몇 주 동안 `ready-for-agent`에 있을 수 있습니다. 그동안 코드베이스는 변경됩니다. 파일이 이름 변경, 이동, 리팩터링되어도 유용하게 유지되도록 브리프를 작성하세요.

- **해야 할 것:** 인터페이스, 타입, 동작 계약 설명
- **해야 할 것:** 에이전트가 찾거나 수정해야 할 특정 타입, 함수 시그니처, 설정 형태 명명
- **하지 말 것:** 파일 경로 참조 — 금방 오래된 정보가 됨
- **하지 말 것:** 행 번호 참조
- **하지 말 것:** 현재 구현 구조가 그대로 유지될 것이라고 가정

### 절차적이 아닌 동작적

시스템이 **무엇을** 해야 하는지 설명하고, **어떻게** 구현할지 설명하지 마세요. 에이전트는 코드베이스를 새로 탐색하고 자신의 구현 결정을 내릴 것입니다.

- **좋음:** "`SkillConfig` 타입은 `CronExpression` 타입의 선택적 `schedule` 필드를 허용해야 함"
- **나쁨:** "src/types/skill.ts를 열고 42번째 줄에 schedule 필드 추가"
- **좋음:** "사용자가 인수 없이 `/triage`를 실행하면 주의가 필요한 이슈 요약을 봐야 함"
- **나쁨:** "메인 핸들러 함수에 switch 문 추가"

### 완전한 인수 기준

에이전트는 언제 완료되었는지 알아야 합니다. 모든 에이전트 브리프에는 구체적이고 테스트 가능한 인수 기준이 있어야 합니다. 각 기준은 독립적으로 검증 가능해야 합니다.

- **좋음:** "`gh issue list --label needs-triage` 실행 시 초기 분류를 거친 이슈 반환"
- **나쁨:** "분류가 올바르게 작동해야 함"

### 명시적 범위 경계

범위에서 제외되는 것을 명시. 에이전트가 골드 플레이팅하거나 인접 기능에 대해 가정하는 것을 방지.

## 템플릿

```markdown
## 에이전트 브리프

**카테고리:** bug / enhancement
**요약:** 무엇이 필요한지 한 줄 설명

**현재 동작:**
지금 일어나는 일 설명. 버그의 경우 깨진 동작.
기능 개선의 경우 이 기능이 구축되는 현상 유지.

**원하는 동작:**
에이전트 작업 완료 후 일어나야 할 일 설명.
엣지 케이스와 오류 조건에 대해 구체적으로.

**주요 인터페이스:**
- `TypeName` — 무엇이 변경되어야 하고 왜 변경되어야 하는지
- `functionName()` 반환 타입 — 현재 반환하는 것 vs 반환해야 하는 것
- 설정 형태 — 필요한 새 설정 옵션

**인수 기준:**
- [ ] 구체적이고 테스트 가능한 기준 1
- [ ] 구체적이고 테스트 가능한 기준 2
- [ ] 구체적이고 테스트 가능한 기준 3

**범위 외:**
- 이 이슈에서 변경되거나 다뤄져서는 안 되는 것
- 관련 있어 보이지만 별개인 인접 기능
```

## 예시

### 좋은 에이전트 브리프 (버그)

```markdown
## 에이전트 브리프

**카테고리:** bug
**요약:** 스킬 description 잘림이 단어 중간에서 끊어져 깨진 출력 생성

**현재 동작:**
스킬 description이 1024자를 초과하면 단어 경계와 관계없이
정확히 1024자에서 잘림. 단어 중간에서 끝나는 description 생성
(예: "사용자가 confi를 원할 때").

**원하는 동작:**
잘림은 1024자 이전의 마지막 단어 경계에서 끊고
잘림을 나타내기 위해 "..."을 추가해야 함.

**주요 인터페이스:**
- `SkillMetadata` 타입의 `description` 필드 — 타입 변경 불필요,
  하지만 이를 채우는 검증/처리 로직이 단어 경계를 존중해야 함
- SKILL.md 프론트매터를 읽고 description을 추출하는 모든 함수

**인수 기준:**
- [ ] 1024자 미만 description은 변경되지 않음
- [ ] 1024자 초과 description은 1024자 이전 마지막 단어 경계에서 잘림
- [ ] 잘린 description은 "..."으로 끝남
- [ ] "..."을 포함한 총 길이는 1024자를 초과하지 않음

**범위 외:**
- 1024자 제한 자체 변경
- 여러 줄 description 지원
```

### 좋은 에이전트 브리프 (기능 개선)

```markdown
## 에이전트 브리프

**카테고리:** enhancement
**요약:** 거부된 기능 요청 추적을 위한 `.out-of-scope/` 디렉터리 지원 추가

**현재 동작:**
기능 요청이 거부되면 `wontfix` 라벨과 코멘트와 함께 이슈가 닫힘.
결정이나 추론에 대한 영구 기록이 없음.
향후 유사한 요청 시 메인테이너가 이전 논의를 기억하거나 검색해야 함.

**원하는 동작:**
거부된 기능 요청은 결정, 추론, 해당 기능을 요청한 모든 이슈 링크를
캡처하는 `.out-of-scope/<concept>.md` 파일에 문서화되어야 함.
새 이슈 분류 시 이 파일들을 확인하여 일치 항목 검사.

**주요 인터페이스:**
- `.out-of-scope/`의 마크다운 파일 형식 — 각 파일은
  `# 개념 이름` 헤딩, `**결정:**` 줄, `**이유:**` 줄,
  그리고 이슈 링크가 있는 `**이전 요청:**` 목록을 가져야 함
- 분류 워크플로우는 모든 `.out-of-scope/*.md` 파일을 조기에 읽고
  개념 유사성으로 들어오는 이슈와 대조해야 함

**인수 기준:**
- [ ] 기능을 wontfix로 닫으면 `.out-of-scope/`에 파일 생성/업데이트
- [ ] 파일에 결정, 추론, 닫힌 이슈 링크 포함
- [ ] 일치하는 `.out-of-scope/` 파일이 이미 존재하면 중복 생성 대신
      새 이슈를 "이전 요청" 목록에 추가
- [ ] 분류 중 기존 `.out-of-scope/` 파일을 확인하고 새 이슈가
      이전 거부와 일치하면 표면화

**범위 외:**
- 자동 매칭 (사람이 일치 확인)
- 이전에 거부된 기능 재개
- 버그 보고 (기능 개선 거부만 `.out-of-scope/`로 이동)
```

### 나쁜 에이전트 브리프

```markdown
## 에이전트 브리프

**요약:** 분류 버그 수정

**할 일:**
분류 관련 뭔가 고장 남. 메인 파일 보고 수정.
150번째 줄 근처 함수에 문제 있음.

**변경할 파일:**
- src/triage/handler.ts (150번째 줄)
- src/types.ts (42번째 줄)
```

나쁜 이유:
- 카테고리 없음
- 모호한 설명 ("분류 관련 뭔가 고장 남")
- 금방 오래될 파일 경로와 행 번호 참조
- 인수 기준 없음
- 범위 경계 없음
- 현재 동작 vs 원하는 동작 설명 없음
