# 모듈 심화

의존성을 고려하여 얕은 모듈 묶음을 안전하게 심화하는 방법입니다. [SKILL.md](SKILL.md)의 **module**, **interface**, **seam**, **adapter** 용어를 사용합니다.

## 의존성 분류

심화할 후보를 평가할 때 의존성을 분류하세요. 의존성 종류에 따라 심화된 모듈을 seam을 통해 테스트하는 방법이 달라집니다.

### 1. 프로세스 내부

순수 계산, 메모리 내 상태 등 I/O가 없는 경우입니다. 언제나 심화할 수 있습니다. 모듈을 합치고 새 interface를 통해 직접 테스트하세요. adapter는 필요하지 않습니다.

### 2. 로컬 대체 가능

로컬 테스트 대역이 있는 의존성입니다(Postgres용 PGLite, 메모리 내 파일 시스템 등). 대역이 있다면 심화할 수 있습니다. 테스트 스위트에서 대역을 실행해 심화된 모듈을 테스트하세요. seam은 내부에 두며 모듈의 외부 interface에는 port를 두지 않습니다.

### 3. 원격이지만 직접 소유(Ports & Adapters)

네트워크를 통해 연결된 자체 서비스(마이크로서비스, 내부 API 등)입니다. seam에 **port**(interface)를 정의하세요. 깊은 모듈이 로직을 소유하고, 전송 수단은 **adapter**로 주입합니다. 테스트에서는 메모리 내 adapter를, 운영 환경에서는 HTTP/gRPC/큐 adapter를 사용하세요.

권장 제안 형태: *"seam에 port를 정의하고 운영 환경에는 HTTP adapter, 테스트에는 메모리 내 adapter를 구현하세요. 그러면 네트워크를 사이에 두고 배포하더라도 로직은 하나의 깊은 모듈에 모입니다."*

### 4. 실제 외부 의존성(Mock)

직접 제어할 수 없는 외부 서비스(Stripe, Twilio 등)입니다. 심화된 모듈이 외부 의존성을 주입받는 port를 갖게 하고, 테스트에서는 mock adapter를 제공하세요.

## Seam 원칙

- **Adapter 하나는 가상의 seam, 둘은 실제 seam입니다.** 최소 두 adapter(보통 운영 환경과 테스트용)가 정당화되지 않는다면 port를 도입하지 마세요. adapter 하나만 있는 seam은 간접 계층에 불과합니다.
- **내부 seam과 외부 seam을 구분하세요.** 깊은 모듈은 자체 테스트에 쓰이는 내부 seam(implementation에만 공개)과 interface에 놓인 외부 seam을 모두 가질 수 있습니다. 테스트에서 사용한다는 이유만으로 내부 seam을 interface에 노출하지 마세요.

## 테스트 전략: 계층을 더하지 말고 교체하기

- 심화된 모듈의 interface에서 테스트하게 되면 기존 얕은 모듈의 단위 테스트는 불필요해집니다. 삭제하세요.
- 심화된 모듈의 interface에서 새 테스트를 작성하세요. **Interface가 테스트 표면입니다.**
- 내부 상태가 아니라 interface를 통해 관찰할 수 있는 결과를 검증하세요.
- 테스트는 implementation이 아닌 동작을 설명하므로 내부 리팩터링 후에도 그대로 통과해야 합니다. implementation이 바뀔 때 테스트도 바꿔야 한다면 interface를 넘어 테스트하고 있는 것입니다.
