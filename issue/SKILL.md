# QA 세션

대화형 QA 세션을 진행하세요. 사용자가 겪는 문제를 설명하면, 명확히 정리하고, 코드베이스에서 맥락을 탐색한 후, 내구성 있고 사용자 중심적이며 프로젝트의 도메인 언어를 사용하는 GitLab 이슈를 등록하세요.

## 사용자가 제기하는 각 이슈마다

### 1. 듣고 가볍게 명확화

사용자가 자신의 말로 문제를 설명하게 하세요. 다음에 초점을 맞춰 **최대 2-3개의 짧은 명확화 질문**을 하세요:

- 기대한 것 vs 실제로 일어난 것
- 재현 단계 (명확하지 않은 경우)
- 일관되게 발생하는지 간헐적인지

과도하게 인터뷰하지 마세요. 설명이 이슈 등록에 충분히 명확하면 넘어가세요.

### 2. 백그라운드에서 코드베이스 탐색

사용자와 대화하는 동안 백그라운드에서 Agent(subagent_type=Explore)를 실행하여 관련 영역을 이해하세요. 목표는 수정 방법을 찾는 것이 아닙니다 — 다음을 파악하는 것입니다:

- 해당 영역에서 사용되는 도메인 언어 학습 (UBIQUITOUS_LANGUAGE.md 확인)
- 기능이 무엇을 해야 하는지 이해
- 사용자 대상 동작 경계 식별

이 맥락은 더 나은 이슈를 작성하는 데 도움이 됩니다 — 하지만 이슈 자체에 특정 파일, 행 번호, 내부 구현 세부사항을 언급해서는 안 됩니다.

### 3. 범위 평가: 단일 이슈인가, 분할인가?

등록하기 전에 이것이 **단일 이슈**인지 여러 이슈로 **분할**해야 하는지 결정하세요.

분할이 필요한 경우:

- 수정이 여러 독립 영역에 걸쳐 있는 경우 (예: "폼 유효성 검사가 잘못됐고, 성공 메시지가 없고, 리다이렉트도 깨졌다")
- 서로 다른 사람이 병렬로 작업할 수 있는 명확히 분리 가능한 관심사가 있는 경우
- 사용자가 여러 개의 뚜렷한 실패 모드나 증상을 설명하는 경우

단일 이슈로 유지할 경우:

- 한 곳에서 한 가지 동작이 잘못된 경우
- 모든 증상이 동일한 근본 동작에서 비롯된 경우

### 4. GitLab 이슈 등록

`glab issue create --repo <namespace>/<project>`로 이슈를 생성하세요. 사용자에게 먼저 검토를 요청하지 마세요 — 바로 등록하고 URL을 공유하세요.

이슈는 **내구성**이 있어야 합니다 — 큰 리팩터링 후에도 여전히 의미가 통해야 합니다. 사용자 관점에서 작성하세요.

#### 단일 이슈의 경우

이 템플릿을 사용하세요:

```bash
glab issue create \
  --repo <project> \
  --title "<간결한 제목>" \
  --description "## 발생한 현상

[사용자가 경험한 실제 동작을 평이한 언어로 설명]

## 기대한 동작

[기대한 동작을 설명]

## 재현 단계

1. [개발자가 따라할 수 있는 구체적이고 번호가 매겨진 단계]
2. [내부 모듈명이 아닌 코드베이스의 도메인 용어 사용]
3. [관련 입력값, 플래그, 설정 포함]

## 추가 맥락

[이슈를 이해하는 데 도움이 되는 사용자 또는 코드베이스 탐색의 추가 관찰 사항 — 예: 'Docker 계층을 사용할 때만 발생하고 파일 시스템 계층에서는 발생하지 않음' — 도메인 언어를 사용하되 파일을 인용하지 말 것]" \
  --label "bug"
```

#### 분할 (여러 이슈)의 경우

의존성 순서(차단하는 것 먼저)로 이슈를 생성하여 실제 이슈 번호를 참조할 수 있게 하세요. 각 하위 이슈에 `--label "bug"`를 적용하세요.

각 하위 이슈에 이 템플릿을 사용하세요:

```bash
glab issue create \
  --repo <project> \
  --title "<간결한 제목>" \
  --description "## 부모 이슈

\#<부모-이슈-번호> (추적 이슈를 생성한 경우) 또는 'QA 세션 중 보고됨'

## 무엇이 잘못됐나

[이 특정 동작 문제를 설명 — 전체 보고가 아닌 이 부분만]

## 기대한 동작

[이 특정 부분에 대한 기대 동작]

## 재현 단계

1. [이 이슈에 특정된 단계]

## 차단 요소

- \#<이슈-번호> (다른 이슈가 해결될 때까지 이 이슈를 수정할 수 없는 경우)

또는 차단 요소가 없으면 '없음 — 즉시 시작 가능'.

## 추가 맥락

[이 부분과 관련된 추가 관찰 사항]" \
  --label "bug"
```

분할 생성 시:

- **두꺼운 이슈 몇 개보다 얇은 이슈 여러 개를 선호하세요** — 각각 독립적으로 수정 및 검증 가능해야 합니다
- **차단 관계를 정직하게 표시하세요** — 이슈 B가 진짜로 이슈 A가 수정될 때까지 테스트할 수 없다면 그렇게 표시하세요. 독립적이라면 둘 다 "없음 — 즉시 시작 가능"으로 표시하세요
- **의존성 순서로 이슈를 생성하세요** — "차단 요소"에서 실제 이슈 번호를 참조할 수 있습니다
- **병렬성을 극대화하세요** — 여러 사람(또는 에이전트)이 서로 다른 이슈를 동시에 가져갈 수 있게 하는 것이 목표입니다

#### 모든 이슈 본문의 규칙

- **파일 경로나 행 번호 금지** — 금방 오래된 정보가 됩니다
- **프로젝트의 도메인 언어 사용** (UBIQUITOUS_LANGUAGE.md가 있으면 확인하세요)
- **코드가 아닌 동작을 설명하세요** — "42번째 줄에서 applyPatch()가 예외를 던짐"이 아니라 "동기화 서비스가 패치 적용에 실패함"
- **재현 단계는 필수** — 파악할 수 없으면 사용자에게 물어보세요
- **간결하게** — 개발자가 30초 안에 이슈를 읽을 수 있어야 합니다
- GitLab 이슈 참조는 `#번호` 형식이고, MR은 `!번호` 형식임을 기억하세요

등록 후 `glab issue list --repo <project>`로 생성된 이슈 번호를 확인하고, 모든 이슈 URL을 출력한 후(차단 관계 요약과 함께) 물어보세요: "다음 이슈, 아니면 끝낼까요?"

### 5. 세션 계속

사용자가 끝났다고 말할 때까지 계속하세요. 각 이슈는 독립적입니다 — 한꺼번에 처리하지 마세요.
