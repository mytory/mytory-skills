# HTML 작업 완료 보고서

작업자와 검토자가 보고서 하나만 열어 **무엇을 했고, 무엇으로 입증했고, 어디를 더 봐야 하는지** 판단하게 한다. 완료를 입증할 책임은 작업한 AI에게 있다. 글보다 증거(영상·측정값·실행 기록)가 먼저다.

영상 촬영 시 브라우저 테스트는 비용 효율적인 값싼 모델로, 추론 수준은 높게(필요하면 최대로) 지정해 실행한다. 검수는 반대로 고성능·고추론 모델에 맡긴다(아래 "검수 전용 AI").

## 작업 시작 시 정할 것

구현·수정 작업을 시작할 때 아래를 한 번에 묻는다. 사용자가 이미 밝힌 것은 다시 묻지 않고, 같은 작업을 이어가는 동안에는 재확인하지 않는다.

1. **보고서**: "이번 작업은 HTML 완료 보고서도 작성할까요?" — "생략" / "작성".
2. **완료 기준**: 요청에서 완료 기준을 뽑아 보여 주고 빠지거나 틀린 것이 있는지 묻는다. 기준마다 아래 표로 증거 종류를 정한다.
3. **증거와 영상**: 변경 유형에 맞는 증거를 추천하고 이유를 한 줄 붙인다. 선택지는 추천안(첫 번째, "(추천)" 표시)과 "영상 생략", 그 밖에 의미 있는 대안만.

   | 변경 유형 | 기본 증거 | 영상 |
   |---|---|---|
   | 화면 버그 수정 | 수정 전후 측정값, 스크린샷 | 전후 비교 영상 |
   | 새 화면·화면 동작 변경 | 스크린샷, 응답 JSON | 작동 시연 영상(수정 후 한 상태) |
   | API·배치·DB 로직 | 테스트 실행 기록, 요청·응답 JSON, DB 전후 값 | 없음 |
   | 리팩터링 | 변경 전후 같은 테스트의 통과 기록 | 없음 |
   | 설정·빌드·문서 | 빌드·린트 실행 기록, 변경된 결과물 | 없음 |

   한 작업에 여러 유형이 섞이면 기준마다 따로 고른다. 화면에서 확인할 수 있는 기능은 영상으로, 그 밖의 동작은 실행 기록으로 입증한다.
4. **음성 설명**: 영상을 찍기로 했으면 "음성 설명(내레이션)을 넣을까요?" — "생략" / "넣기". 영상 종류와 별개의 선택이다. Supertonic을 쓸 수 없으면 이유를 말하고 이 질문을 빼고 생략으로 진행한다.
5. **프레젠테이션 영상**: 다른 사람에게 검토를 요청하는 작업이거나 위험도가 **높음**(아래 "위험도")일 때만 묻는다. 내레이션이 필수라서 Supertonic을 쓸 수 없으면 묻지 않는다. "보고서를 설명하는 프레젠테이션 영상도 만들까요?" — "생략" / "작성".

- 답변을 기다리는 동안 본 작업은 계속 진행한다. 작성한다는 답변이 없으면 보고서 파일을 만들지 않고, 완료 시 대화로 변경 내용과 검증 결과를 간단히 전달한다.
- 보고서 생략 여부와 관계없이 완료 기준을 입증하는 검증과 검수 전용 AI 검수는 수행한다.

## 위험도

검토자가 보고서만 볼지, 증거까지 볼지, 코드를 직접 볼지 정하는 근거다. 가장 높은 항목 하나로 정하고 이유를 적는다.

| 위험도 | 해당하는 변경 | 권장 검토 방식 |
|---|---|---|
| 높음 | 인증·권한·결제·개인정보, DB 스키마·데이터 변경, 여러 기능이 쓰는 공용 코드, 되돌리기 어려운 배포·마이그레이션 | 코드 직접 검토 |
| 중간 | 사용자가 보는 동작 변경, 외부 계약(API 형식)을 유지한 로직 변경 | 영상·증거 확인 |
| 낮음 | 문구·스타일, 테스트·문서만 변경, 영향 범위가 한 화면 안 | 보고서 확인 |

## 폴더와 파일 이름

파일 하나가 아니라 폴더로 만든다. **폴더 이름과 보고서 파일 이름은 `YYYY-MM-DD {주제 혹은 이슈번호}`** — 날짜, 공백 한 칸, 주제. 밑줄(`_`)로 잇지 않는다. 보고서 파일은 폴더와 같은 이름에 `.html`.

```
docs/2026-10-04 issue-470 후속/
  2026-10-04 issue-470 후속.html      ← 보고서(폴더와 같은 이름)
  videos/       final.mp4 또는 final-narrated.mp4, presentation-narrated.mp4, .srt/.vtt, clips/
  screenshots/  final/NN-설명.webp    (PNG 금지 — 아래 "스크린샷")
  evidence/     실행 기록(.log), 응답 JSON, DB 전후 값, 측정 로그
  reviews/      검수 AI·코드 리뷰 원문
```

- 주제 자리에는 이슈 번호(`issue-470`, `#478`)나 짧은 주제를 쓴다. 둘 다 있으면 `2026-10-04 issue-470 악성 프로그램 관리`처럼 이슈 번호를 앞에.
- 날짜는 보고서를 쓴 날. 같은 주제를 다시 보고하면 새 날짜로 새 폴더를 만들거나, 같은 폴더에 `YYYY-MM-DD {주제} v2.html`을 두고 이전 보고서를 머리말에서 링크한다.
- 폴더를 둘 위치는 프로젝트의 문서 관례를 따른다(보통 `docs/` 바로 아래나 `docs/<이슈>/`). 관례가 없으면 사용자에게 묻는다.
- 보고서와 함께 두는 다른 문서(전달 문서, 커밋 계획 등)도 같은 형식: `YYYY-MM-DD {주제}.md`.
- 폴더 안의 영상·스크린샷·증거 파일은 짧은 ASCII 이름(`final.mp4`, `31-rules-list.webp`). 경로에 공백이 있으니 셸에서는 따옴표로 감싸고, HTML의 `src`·`href`는 상대 경로라 영향이 없다.
- 영상을 OS 동영상 폴더에 두지 않는다. 경로는 모두 상대 경로.

## 절차

1. **템플릿을 복사한다.** `assets/report-template.html` → `YYYY-MM-DD {주제}/YYYY-MM-DD {주제}.html`. `{{ }}`를 채우고 안내 주석과 해당 없는 절을 지운다.
2. **실행 기록을 남긴다.** 테스트·빌드·스크립트 실행은 이 스킬 폴더의 `scripts/run-evidence.sh <보고서폴더>/evidence/NN-이름.log <명령...>`으로 프로젝트 폴더에서 돌린다. 파이프·환경 변수가 필요하면 `bash -c '...'`로 감싼다. 실행 시각, 커밋 해시(미커밋 변경 여부), 명령, 전체 출력, 종료 코드가 파일에 남는다. 보고서의 수치는 이 파일에서 옮기고 파일을 링크한다. 리팩터링은 같은 테스트를 변경 전 커밋과 후 커밋에서 각각 남긴다.
3. **영상을 찍는다(작업 시작 시 영상을 고른 경우만).** `browser-repro-video` 스킬. 전후 비교는 같은 조작을 상태별로, 작동 시연은 수정 후 한 상태로 찍는다. 구간 시작 시각은 `concat-clips.sh` 출력에서 가져와 표에 적는다.
4. **음성 설명을 입힌다(고른 경우만).** `browser-repro-video`의 `narrate.mjs`(내부에서 `supertonic-tts` 스킬의 Supertonic 3 사용). 화면 캡션과 별도로 읽기용 대본을 쓰고, 내레이션 본(`-narrated.mp4`)을 주 영상으로 한다. 정지 허용은 내레이션이 흐르는 장면 30초, 소리 없는 장면 5초.
5. **스크린샷을 WebP로 바꾼다.** `scripts/to-webp.sh <보고서폴더>` — PNG를 WebP(q82)로 바꾸고 HTML 참조까지 고친다.
6. **검수 전용 AI로 검수한다.** 아래 "검수 전용 AI". 지적을 고쳤으면 해당 증거를 다시 만들고 다시 검수한다.
7. **실제 브라우저로 검사한다.** `node scripts/check-report.mjs "<보고서>.html"`(playwright-core가 있는 폴더에서). 깨진 이미지·영상, 없는 파일을 가리키는 링크, 남은 `{{ }}`, 접힌 영역 안의 `warn`·`bad` 판정이 있으면 종료 코드 1.
8. **프레젠테이션 영상을 만든다(고른 경우만).** 보고서가 완성된 뒤 `browser-repro-video`의 `present-report.mjs`로 보고서를 절별로 스크롤하며 녹화하고 내레이션을 입힌다. `videos/presentation-narrated.mp4`로 두고 머리말의 프레젠테이션 링크를 채운 뒤 7을 다시 돌린다.
9. **경로를 알려 준다.** 보고서 절대 경로, 영상 길이, 위험도와 검토자 확인 지점, 남은 외부 작업.

## 검수 전용 AI

코드를 작성하지 않은 AI가 검수한다. 작성한 AI의 자기 점검은 검수로 치지 않는다.

- **누가**: 서브 에이전트로 띄운다. 고성능·고추론 모델이 좋고, 다른 개발사의 모델이나 `open-code-review` 스킬(`ocr`)도 쓸 수 있다. 위험도가 높음이면 서로 다른 모델·도구로 두세 번 검수한다.
- **무엇을 주는가**: 완료 기준, 변경 diff(또는 커밋 범위), 보고서 폴더 경로. 작성한 AI의 추론 과정이나 "잘 됐다"는 요약은 주지 않는다. 주장을 반박할 근거를 찾으라고 지시한다.
- **무엇을 보는가**:
  - 코드: 버그, 보안, 요구 누락, 프로젝트 방향과 어긋나는 부분.
  - 보고서: 판정과 수치마다 증거 파일이 실제로 뒷받침하는가. 실행 기록의 커밋 해시가 최종 코드와 같은가. 영상·스크린샷이 최종 코드 상태인가(프레임을 뽑아 본다).
  - 테스트: 완료 기준을 실제로 검증하는가. 항상 통과하는 단언, 지나친 목(mock), 지운·건너뛴 테스트가 없는가.
- 원문은 `reviews/`에 저장하고 보고서의 "검수" 절에 회차별 건수와 조치를 적는다. 고치지 않은 지적은 이유와 함께 남긴다.
- 같은 지적이 5회 반복되면 멈추고 실패 보고서를 쓴다.

## 내용 규칙

- **머리말 바로 아래에 검토 안내.** 위험도와 이유, 권장 검토 방식, 검토자가 추가로 확인할 곳(`파일:줄`과 이유)을 둔다. 검토자는 이 절과 완료 기준 표만 보고도 다음 행동을 정할 수 있어야 한다.
- **완료 기준 표가 그다음.** 기준마다 한 줄: 기준, 증거 종류, 증거(파일 링크·영상 구간), 판정(`ok`/`warn`/`bad`). 커밋·푸시·이슈 코멘트 같은 남은 외부 작업은 `warn`으로 마지막 줄.
- **필수 검토가 아닌 내용은 `<details>`로 접는다.** 절 제목과 결론 한 줄은 밖에 두고 본문만 접는다. `<summary>`에는 펼치지 않아도 알 수 있는 결론을 쓴다(예: "검수 2회, 남은 지적 0건"). 접는 대상: 설계 결정, 검수 원문 요약, 테스트 코드 변경 목록, 실행 기록 목록, 검수 기록(질문과 답), 보조 스크린샷. 접지 않는 대상: 검토 안내, 완료 기준, 영상, 요청 반영, DB·외부 영향, 범위 밖·남은 위험, 그리고 `warn`·`bad` 판정이나 검토자 확인 지점이 걸린 내용.
- **요청이 여러 건이면 번호 그대로 반영 표를 만든다.** 사용자가 준 순서와 표현을 유지하고, 처리 칸에는 무엇을 바꿨는지와 **확인 방법·증거 파일**을 적는다.
- **전/후 비교는 측정값으로.** "깨지지 않음" 대신 `scrollWidth 11,293 → 1,390`. 값은 `evidence/`의 파일에서 가져온다.
- **로직 설명은 간단히.** 입력에서 결과까지의 주요 처리 순서와 그 방식을 택한 이유를 기능별로 2~4문장에 담는다. 구현을 전부 나열하지 않는다.
- **테스트 코드 변경 목록을 적는다.** 이번 작업에서 새로 만들거나 수정한 테스트 파일마다 테스트 메서드·케이스 이름, 추가·수정·삭제한 내용, 검증하는 동작을 적는다. 한 파일의 여러 메서드가 바뀌면 각각 적는다. 테스트 코드 변경이 없다면 "없음"이라고 명시한다. 테스트 실행 결과는 별도의 검증 항목에 적는다.
- **설계 결정은 누가 정했는지 적는다**(사용자 결정 / 내 판단). 검수 AI 권장과 다르게 간 것은 이유와 함께.
- **검증에는 실제로 실행한 것만.** 못 한 것은 "미확인", 추정은 추정이라고 쓴다. 수치에는 실행 기록 파일을 링크한다.
- **검수 기록(선택).** 사용자가 변경 내용을 AI에게 묻고 답을 받았다면 핵심 질문과 답을 짧게 남긴다. 없으면 절을 지운다.
- **캡션이 영상에 박혀 있으면 `<track>`을 달지 않는다**(겹치고, `file://`에서는 Chrome이 막는다). 자막을 따로 붙여야 하면 `browser-repro-video`의 `references/captions.md`(Blob 방식).
- **영상 구간 제목과 시작 시각은 클릭 가능한 버튼으로 쓴다.** 같은 행의 두 `video-seek` 버튼에 표시 시각과 일치하는 실제 시작 초를 동일한 `data-video-seek`로 넣고, `data-video-target`은 대상 영상의 `id`와 맞춘다. 예: `1:23`은 `data-video-seek="83"`. 시각 이동용 스크립트를 유지하며, 제목이나 시각을 클릭하면 해당 구간으로 이동하고 재생·일시정지 상태를 유지한다.
- **영상·스크린샷과 코드가 어긋나면 다시 찍는다.** 보고서 문구("촬영 시점에는 …")로 메우지 않는다. 화면에 보이는 변경을 나중에 더 했다면 해당 구간 재촬영까지가 완료다.
- 재보고일 때는 이전 보고서를 지우지 않고 새 보고서 머리말에서 링크한다(이름 규칙은 위 "폴더와 파일 이름").
- 템플릿의 색·글꼴·간격은 그대로 쓴다. 판정 색은 `ok`/`warn`/`bad`, 위험도 색은 `risk-low`/`risk-mid`/`risk-high` 클래스로만 바꾼다.

## 스크린샷

- **WebP로 저장한다.** Playwright·agent-browser는 PNG로 찍으므로 찍은 뒤 `to-webp.sh`로 변환한다(화면 캡처는 보통 1/3~1/5로 줄어든다). 글자가 뭉개지면 품질을 올린다: `to-webp.sh <폴더> 90`.
- 파일명은 `NN-설명.webp`(ASCII), 구간 번호를 앞자리로(`31-rules-list.webp`).
- 확인 대상이 화면에 보이게 **스크롤해서** 찍는다. 캡션(`figcaption`)에는 "이 화면에서 봐야 할 것"을 쓴다.
- 설명 글·패널은 확인 대상을 가리면 안 된다. 스크린샷 위에 덧그리지 말고 `figcaption`에 쓴다. 영상 캡션은 `browser-repro-video`의 규칙대로 화면 밖 띠에 둔다. 캡션의 숫자는 화면에서 눈으로 셀 수 있는 것과 같아야 한다.
- 썸네일은 가로·세로 원본 비율과 관계없이 동일한 `16/10` 프레임에 `object-fit:contain`으로 넣는다. 같은 폭의 그리드에서는 높이가 같고 이미지 전체가 잘리지 않으며, 자세한 내용은 클릭해서 원본을 크게 본다.
- 템플릿의 이미지 보기용 `<dialog>`·스타일·스크립트를 유지한다. `main` 안의 `figure img`는 클릭 또는 Enter·Space로 크게 열리고, 버튼 또는 좌우 방향키로 보고서 순서대로 이동한다. 첫 이미지의 이전 버튼과 마지막 이미지의 다음 버튼은 비활성화하며 순환하지 않는다. 닫기 버튼·Esc·바깥 배경 클릭으로 닫으면 열었던 이미지로 키보드 초점이 돌아온다.
