# HTML 작업 완료 보고서

작업자와 검토자가 보고서 하나만 열어 **무엇을 했고, 무엇으로 입증했고, 어디를 더 봐야 하는지** 판단하게 한다. 완료를 입증할 책임은 작업한 AI에게 있다. 글보다 증거(영상·측정값·실행 기록)가 먼저다.

영상 촬영 시 브라우저 테스트는 비용 효율적인 값싼 모델로, 추론 수준은 높게(필요하면 최대로) 지정해 실행한다. 검수는 반대로 고성능·고추론 모델에 맡긴다(아래 "검수 전용 AI").

## 작업 시작 시 정할 것

구현·수정 작업을 시작할 때 아래를 한 번에 묻는다. 사용자가 이미 밝힌 것은 다시 묻지 않고, 같은 작업을 이어가는 동안에는 재확인하지 않는다.

1. **보고서**: "이번 작업은 HTML 완료 보고서도 작성할까요?" — "생략" / "작성".
2. **완료 기준**: 요청에서 완료 기준을 뽑아 보여 주고 빠지거나 틀린 것이 있는지 묻는다. 기준마다 아래 표로 증거 종류를 정한다.
3. **증거와 영상**: 변경 유형에 맞는 증거를 추천하고 이유를 한 줄 붙인다. 선택지는 추천안(첫 번째, "(추천)" 표시)과 "영상 생략", 그 밖에 의미 있는 대안만.

   | 변경 유형 | 기본 증거 | 영상 |
   |---|---|---|
   | 화면 버그 수정 | 수정 전후 측정값, 스크린샷 | 전후 비교 영상 |
   | 새 화면·화면 동작 변경 | 스크린샷, 응답 JSON | 작동 시연 영상(수정 후 한 상태) |
   | API·배치·DB 로직 | 테스트 실행 기록, 요청·응답 JSON, DB 전후 값 | 없음 |
   | 리팩터링 | 변경 전후 같은 테스트의 통과 기록 | 없음 |
   | 설정·빌드·문서 | 빌드·린트 실행 기록, 변경된 결과물 | 없음 |

   한 작업에 여러 유형이 섞이면 기준마다 따로 고른다. 화면에서 확인할 수 있는 기능은 영상으로, 그 밖의 동작은 실행 기록으로 입증한다.
4. **음성 설명**: 영상을 찍기로 했으면 "음성 설명(내레이션)을 넣을까요?" — "생략" / "넣기". 영상 종류와 별개의 선택이다. Supertonic을 쓸 수 없으면 이유를 말하고 이 질문을 빼고 생략으로 진행한다.
5. **요약 발표 자료**: 내용이 많고 복잡해서 보고서만으로는 흐름을 한눈에 잡기 어려울 때만 묻는다. 예: 요청·완료 기준이 여러 건, 여러 기능이나 변경 유형이 섞임, 기존 동작 변경이 여러 건, 로직이 여러 단계를 거침. 위험도로 정하지 않는다. 위험도가 높아도 내용이 단순하면 보고서로 충분하다. 되도록 작업 시작 시, 계획을 세운 직후에 복잡해 보이면 다른 질문과 함께 묻는다. 구현하면서 복잡해졌다면 보고서를 쓰기 전이나 쓴 뒤에 물어도 된다. "핵심을 요약한 발표 자료도 만들까요?" — "텍스트 슬라이드(Marp HTML, 빠름)" / "프레젠테이션 영상(내레이션 포함, 오래 걸림)" / "생략". 목적은 영상이 아니라 핵심 전달이므로 둘 중 하나만 만든다. Supertonic을 쓸 수 없으면 이유를 말하고 영상 선택지를 뺀다.

- 답변을 기다리는 동안 본 작업은 계속 진행한다. 작성한다는 답변이 없으면 보고서 파일을 만들지 않고, 완료 시 대화로 변경 내용과 검증 결과를 간단히 전달한다.
- 보고서 생략 여부와 관계없이 완료 기준을 입증하는 검증과 검수 전용 AI 검수는 수행한다.

## 위험도

검토자가 보고서만 볼지, 증거까지 볼지, 코드를 직접 볼지 정하는 근거다. 가장 높은 항목 하나로 정하고 이유를 적는다.

| 위험도 | 해당하는 변경 | 권장 검토 방식 |
|---|---|---|
| 높음 | 인증·권한·결제·개인정보, DB 스키마·데이터 변경, 여러 기능이 쓰는 공용 코드, 되돌리기 어려운 배포·마이그레이션 | 코드 직접 검토 |
| 중간 | 사용자가 보는 동작 변경, 외부 계약(API 형식)을 유지한 로직 변경 | 영상·증거 확인 |
| 낮음 | 문구·스타일, 테스트·문서만 변경, 영향 범위가 한 화면 안 | 보고서 확인 |

## 폴더와 파일 이름

파일 하나가 아니라 폴더로 만든다. **폴더 이름과 보고서 파일 이름은 `YYYY-MM-DD {주제 혹은 이슈번호}`** — 날짜, 공백 한 칸, 주제. 밑줄(`_`)로 잇지 않는다. 보고서 파일은 폴더와 같은 이름에 `.html`.

```
reports/2026-10-04 issue-470 후속/
  2026-10-04 issue-470 후속.html      ← 보고서(폴더와 같은 이름)
  videos/       final.mp4 또는 final-narrated.mp4, presentation-narrated.mp4, .srt/.vtt, clips/
  screenshots/  final/NN-설명.webp    (PNG 금지 — 아래 "스크린샷")
  evidence/     실행 기록(.log), 응답 JSON, DB 전후 값, 측정 로그
  reviews/      검수 AI·코드 리뷰 원문
  slides/       presentation.md, presentation.html (텍스트 슬라이드를 고른 경우)
```

- 주제 자리에는 이슈 번호(`issue-470`, `#478`)나 짧은 주제를 쓴다. 둘 다 있으면 `2026-10-04 issue-470 악성 프로그램 관리`처럼 이슈 번호를 앞에.
- 날짜는 보고서를 쓴 날. 같은 주제를 다시 보고하면 새 날짜로 새 폴더를 만들거나, 같은 폴더에 `YYYY-MM-DD {주제} v2.html`을 두고 이전 보고서를 머리말에서 링크한다.
- 위치 우선순위는 사용자가 지정한 경로, 프로젝트의 문서 관례, 기본값 `reports/` 순이다.
- 보고서와 함께 두는 다른 문서(전달 문서, 커밋 계획 등)도 같은 형식: `YYYY-MM-DD {주제}.md`.
- 폴더 안의 영상·스크린샷·증거 파일은 짧은 ASCII 이름(`final.mp4`, `31-rules-list.webp`). 경로에 공백이 있으니 셸에서는 따옴표로 감싸고, HTML의 `src`·`href`는 상대 경로라 영향이 없다.
- 영상을 OS 동영상 폴더에 두지 않는다. 경로는 모두 상대 경로.

## 절차

1. **템플릿을 복사한다.** `assets/report-template.html` → `YYYY-MM-DD {주제}/YYYY-MM-DD {주제}.html`. `{{ }}`를 채우고 안내 주석과 해당 없는 절을 지운다.
2. **실행 기록을 남긴다.** 테스트·빌드·스크립트 실행은 이 스킬 폴더의 `scripts/run-evidence.sh <보고서폴더>/evidence/NN-이름.log <명령...>`으로 프로젝트 폴더에서 돌린다. 파이프·환경 변수가 필요하면 `bash -c '...'`로 감싼다. 실행 시각, 커밋 해시(미커밋 변경 여부), 명령, 전체 출력, 종료 코드가 파일에 남는다. 보고서의 수치는 이 파일에서 옮기고 파일을 링크한다. 리팩터링은 같은 테스트를 변경 전 커밋과 후 커밋에서 각각 남긴다.
3. **영상을 찍는다(작업 시작 시 영상을 고른 경우만).** `browser-repro-video` 스킬. 전후 비교는 같은 조작을 상태별로, 작동 시연은 수정 후 한 상태로 찍는다. 저장 폴더는 영상 `videos/`, 결과 스크린샷 `screenshots/final/`, 응답 JSON·DB 전후 값 `evidence/`로 지정한다. 캡션 띠 색은 `REC_THEME=<이 스킬 폴더>/assets/video-theme.json`으로 주입해 보고서와 맞춘다. 프레젠테이션 영상도 같다. 구간 시작 시각은 `concat-clips.sh` 출력에서 가져와 표에 적는다.
4. **음성 설명을 입힌다(고른 경우만).** `browser-repro-video`의 `narrate.mjs`(내부에서 `supertonic-tts` 스킬의 Supertonic 3 사용). 화면 캡션과 별도로 읽기용 대본을 쓰고, 내레이션 본(`-narrated.mp4`)을 주 영상으로 한다. 정지 허용은 내레이션이 흐르는 장면 30초, 소리 없는 장면 5초.
5. **스크린샷을 WebP로 바꾼다.** `scripts/to-webp.sh <보고서폴더>` — PNG를 WebP(q82)로 바꾸고 HTML 참조까지 고친다.
6. **검수 전용 AI로 검수한다.** 아래 "검수 전용 AI". 지적을 고쳤으면 해당 증거를 다시 만들고 다시 검수한다.
7. **실제 브라우저로 검사한다.** `node scripts/check-report.mjs "<보고서>.html"`(playwright-core가 있는 폴더에서). 깨진 이미지·영상, 없는 파일을 가리키는 링크, 남은 `{{ }}`, 접힌 영역 안의 `warn`·`bad` 판정, 요구사항 요약(`#requirements`)이 없거나 5줄을 넘는 경우에 종료 코드 1.
8. **요약 발표 자료를 만든다(고른 경우만).** 보고서가 완성된 뒤 보고서 내용만으로 만든다. 순서는 요구사항 → 검토 안내(위험도·확인 지점) → 완료 기준 → 영상·핵심 구현 → 남은 위험을 기본으로 하고, 보고서에 없는 내용은 넣지 않는다.
   - 텍스트 슬라이드: 아래 "텍스트 슬라이드". `slides/presentation.html`.
   - 프레젠테이션 영상: `browser-repro-video`의 `present-report.mjs`로 보고서를 절별로 스크롤하며 녹화하고 내레이션을 입힌다. 장면 선택자는 위 순서대로 `#requirements` → `#review-guide` → `#criteria` → 영상·핵심 구현 → `#risks`. 저장 폴더는 `videos/`, 결과는 `videos/presentation-narrated.mp4`.

   머리말의 발표 자료 링크를 채운 뒤 7을 다시 돌린다.
9. **브라우저로 열거나 SSH에서 전달한다.** SSH는 알려진 실행 환경 정보 또는 `SSH_CONNECTION`, `SSH_CLIENT`, `SSH_TTY`로 판별한다. SSH이면 완료된 보고서 폴더 전체(증거와 자산 포함)를 폴더 옆에 압축하고 목록을 확인한 뒤, 사용자에게 아카이브 절대 경로, 로컬 PC에서 실행할 `scp` 명령, 압축 해제 명령, 압축 푼 폴더 기준 HTML 상대 경로를 알려 준다. 호스트·별칭·사용자·포트는 확인된 값만 쓰고, `SSH_CONNECTION`의 클라이언트 주소로 접속 대상을 추론하지 않는다. 값이 없으면 `<확인된 호스트>` 같은 자리표시자를 두며, 비기본 포트는 `scp -P <포트>`로 표시하고 공백이 있는 경로는 따옴표로 감싼다.
   ```sh
   tar -czf "<보고서폴더>.tar.gz" -C "<부모폴더>" "<폴더이름>"
   tar -tzf "<보고서폴더>.tar.gz"
   ```
   ```sh
   scp "<사용자>@<확인된 호스트 또는 별칭>:<원격 아카이브 절대 경로>" "<로컬 저장 폴더>/"
   tar -xzf "<로컬 저장 폴더>/<아카이브 파일명>" -C "<압축 해제 폴더>"
   ```
   SSH가 아니면 HTML 보고서를 사용자의 기본 브라우저로 연다(macOS `open "<보고서>.html"`, Linux `xdg-open`, Windows `start "" "<보고서>.html"`). 두 경우 모두 보고서 절대 경로, 영상 길이, 위험도와 검토자 확인 지점, 남은 외부 작업을 알려 준다.

## 검수 전용 AI

코드를 작성하지 않은 AI가 검수한다. 작성한 AI의 자기 점검은 검수로 치지 않는다.

- **필수 코드 검수**: Open Code Review를 사용할 수 있으면 [기본 OCR](../open-code-review/SKILL.md)과 [OCR Delegate](../open-code-review-delegate/SKILL.md)를 **둘 다 반드시 실행한다**. 기본 OCR은 설정된 LLM 제공자로 실행하고, OCR Delegate는 코드를 작성하지 않은 **고성능·고추론 모델**의 서브 에이전트가 수행한다. 두 검수는 같은 최종 변경 범위를 대상으로 하며 일반 서브 에이전트 리뷰로 대체하지 않는다.
- **사용 가능 여부와 실패**: 각 OCR 스킬의 실행·문제 해결 절차를 따른다. 설치·제공자·모델 접근 문제로 어느 한 검수를 실행하지 못하면 원인과 미검수 범위를 보고서에 명시한다. 다른 검수 결과만으로 두 검수를 모두 완료했다고 판정하지 않는다.
- **보고서·증거 검수**: 코드를 작성하지 않은 서브 에이전트가 별도로 확인한다. 기본 OCR과 OCR Delegate의 코드 검수 결과를 보고서·영상·증거 검수 결과와 구분한다.
- **무엇을 주는가**: 완료 기준, 변경 diff(또는 커밋 범위), 보고서 폴더 경로. 작성한 AI의 추론 과정이나 "잘 됐다"는 요약은 주지 않는다. 주장을 반박할 근거를 찾으라고 지시한다.
- **무엇을 보는가**:
  - 코드: 버그, 보안, 요구 누락, 프로젝트 방향과 어긋나는 부분.
  - 보고서: 판정과 수치마다 증거 파일이 실제로 뒷받침하는가. 실행 기록의 커밋 해시가 최종 코드와 같은가. 영상·스크린샷이 최종 코드 상태인가(프레임을 뽑아 본다). 0건 판정마다 양성 대조가 있는가.
  - 테스트: 완료 기준을 실제로 검증하는가. 항상 통과하는 단언, 지나친 목(mock), 지운·건너뛴 테스트가 없는가.
- 원문은 `reviews/`에 저장하고 보고서의 "AI 검수" 절에 회차별 건수와 조치를 적는다. 고치지 않은 지적은 이유와 함께 남긴다.
- 같은 지적이 5회 반복되면 멈추고 실패 보고서를 쓴다.

## 내용 규칙

- **문장은 컴퓨터공학 3학년이 이해할 수 있는 수준으로 비교적 쉽게 쓴다.** 읽는 사람은 이 프로젝트의 맥락을 안다. 전공 기본 지식을 넘는 개념(프레임워크 내부 동작, 동시성·보안의 세부 원리 등)이 나오면 풀어 쓴다. 문장 쓰는 법은 `report-notice-writing` 스킬의 규칙을 기본으로 따르고, 이 스킬의 규칙과 다르면 이 스킬을 따른다.
- **머리말 바로 아래에 요구사항 요약.** 보고서 맨 앞에서 "무엇을 만든 건지"를 먼저 알 수 있어야 한다. 5줄 이내(줄마다 한 가지)로, 사용자가 쓴 표현을 유지한다. 방법·증거·판정은 여기 쓰지 않고 아래 절로 넘긴다. 줄이 넘칠 것 같으면 늘리지 말고 묶는다.
- **그다음에 검토 안내.** 위험도와 이유, 권장 검토 방식, 검토자가 추가로 확인할 곳(`파일:줄`과 이유)을 둔다. 검토자는 이 절과 완료 기준 표만 보고도 다음 행동을 정할 수 있어야 한다.
- **기존 동작을 바꿨으면 검토 안내 맨 앞에 "기존 동작 변경 — 반드시 확인" 블록(`warn`)을 둔다.** 요구가 명시하지 않았는데 작업 전부터 있던 동작이 달라진 것만 모은다. 항목마다 무엇이 바뀌었나, 원래 동작(`git show <기준 브랜치>:파일`로 확인한 `파일:줄`), 바꾼 근거와 그 강도(명시 / 해석 / 내 판단), 되돌리면 생기는 영향, 확인 상태를 적는다. 요구 문서끼리 어긋나 내 판단으로 바꾼 것은 맨 위에 둔다. 요약에도 "기존 동작 변경 N건 — 검토 안내 첫 블록"을 한 줄로 적는다. 없으면 "기존 동작 변경 없음"과 확인 방법을 적는다. 작업 중에 멈춰서 묻는 대신 이 블록으로 검토자가 반드시 보게 한다.
- **완료 기준 표가 그다음.** 기준마다 한 줄: 기준, 증거 종류, 증거(파일 링크·영상 구간), 판정(`ok`/`warn`/`bad`). 커밋·푸시·이슈 코멘트 같은 남은 외부 작업은 `warn`으로 마지막 줄.
- **필수 검토가 아닌 내용은 `<details>`로 접는다.** 절 제목과 결론 한 줄은 밖에 두고 본문만 접는다. `<summary>`에는 펼치지 않아도 알 수 있는 결론을 쓴다(예: "검수 2회, 남은 지적 0건"). 접는 대상: 설계 결정, 검수 원문 요약, 테스트 코드 변경 목록, 실행 기록 목록, 질문과 답, 보조 스크린샷. 접지 않는 대상: 요구사항, 검토 안내, 완료 기준, 영상, 요청 반영, DB·외부 영향, 범위 밖·남은 위험, 그리고 `warn`·`bad` 판정이나 검토자 확인 지점이 걸린 내용.
- **요청이 여러 건이면 번호 그대로 반영 표를 만든다.** 사용자가 준 순서와 표현을 유지하고, 처리 칸에는 무엇을 바꿨는지와 **확인 방법·증거 파일**을 적는다.
- **전/후 비교는 측정값으로.** "깨지지 않음" 대신 `scrollWidth 11,293 → 1,390`. 값은 `evidence/`의 파일에서 가져온다.
- **0건만으로 입증하지 말고 양성 대조를 함께 보인다.** "오류 0건", "검색 결과 0건", "남은 행 0개"는 검사가 잘못돼도 나온다. 같은 검사가 있어야 할 것을 실제로 잡아내는 기록을 함께 남긴다. 예: 수정 전 커밋에서는 같은 검색이 3건을 찾음, 일부러 넣은 잘못된 값 1건은 잡아냄. 양성 대조를 못 했으면 판정을 `warn`으로 두고 이유를 적는다.
- **로직 설명은 간단히.** 입력에서 결과까지의 주요 처리 순서와 그 방식을 택한 이유를 기능별로 2~4문장에 담는다. 구현을 전부 나열하지 않는다.
- **테스트 코드 변경 목록을 적는다.** 이번 작업에서 새로 만들거나 수정한 테스트 파일마다 테스트 메서드·케이스 이름, 추가·수정·삭제한 내용, 검증하는 동작을 적는다. 한 파일의 여러 메서드가 바뀌면 각각 적는다. 테스트 코드 변경이 없다면 "없음"이라고 명시한다. 테스트 실행 결과는 별도의 검증 항목에 적는다.
- **설계 결정은 누가 정했는지 적는다**(사용자 결정 / 내 판단). 검수 AI 권장과 다르게 간 것은 이유와 함께.
- **검증에는 실제로 실행한 것만.** 못 한 것은 "미확인", 추정은 추정이라고 쓴다. 수치에는 실행 기록 파일을 링크한다.
- **증거물을 만드는 과정의 자체 점검과 뒷정리는 쓰지 않는다.** 영상 정지 구간 검사, 프레임 확인, 내레이션 길이 맞춤, 스크린샷 변환처럼 증거물의 품질을 맞추는 일은 기준을 통과시키고 끝낸다. 테스트용 계정·데이터 삭제, 서버 종료, 임시 파일 정리 같은 뒷정리도 마찬가지다. 그 과정이나 결과(예: "정지 검사가 7구간을 보고했지만 다시 재니 최장 4.2초", "테스트 계정을 지웠다")는 보고서에 적지 않는다. 정리하지 못해 남은 것이 있을 때만 남은 위험에 적는다. 보고서에는 작업 결과를 입증하는 내용만 담는다.
- **질문과 답(선택).** 사용자가 변경 내용을 AI에게 묻고 답을 받았다면 핵심 질문과 답을 짧게 남긴다. 없으면 절을 지운다.
- **캡션이 영상에 박혀 있으면 `<track>`을 달지 않는다**(겹치고, `file://`에서는 Chrome이 막는다). 자막을 따로 붙여야 하면 [references/captions-in-html.md](references/captions-in-html.md)(Blob 방식).
- **영상 구간 제목과 시작 시각은 클릭 가능한 버튼으로 쓴다.** 같은 행의 두 `video-seek` 버튼에 표시 시각과 일치하는 실제 시작 초를 동일한 `data-video-seek`로 넣고, `data-video-target`은 대상 영상의 `id`와 맞춘다. 예: `1:23`은 `data-video-seek="83"`. 시각 이동용 스크립트를 유지하며, 제목이나 시각을 클릭하면 해당 구간으로 이동하고 재생·일시정지 상태를 유지한다.
- **영상·스크린샷과 코드가 어긋나면 다시 찍는다.** 보고서 문구("촬영 시점에는 …")로 메우지 않는다. 화면에 보이는 변경을 나중에 더 했다면 해당 구간 재촬영까지가 완료다.
- 재보고일 때는 이전 보고서를 지우지 않고 새 보고서 머리말에서 링크한다(이름 규칙은 위 "폴더와 파일 이름").
- 템플릿의 색·글꼴·간격은 그대로 쓴다. 템플릿 색을 바꾸면 `assets/video-theme.json`도 같이 바꾼다. 판정 색은 `ok`/`warn`/`bad`, 위험도 색은 `risk-low`/`risk-mid`/`risk-high` 클래스로만 바꾼다.

## 스크린샷

- **WebP로 저장한다.** Playwright·agent-browser는 PNG로 찍으므로 찍은 뒤 `to-webp.sh`로 변환한다(화면 캡처는 보통 1/3~1/5로 줄어든다). 글자가 뭉개지면 품질을 올린다: `to-webp.sh <폴더> 90`.
- 파일명은 `NN-설명.webp`(ASCII), 구간 번호를 앞자리로(`31-rules-list.webp`).
- 확인 대상이 화면에 보이게 **스크롤해서** 찍는다. 캡션(`figcaption`)에는 "이 화면에서 봐야 할 것"을 쓴다.
- 설명 글·패널은 확인 대상을 가리면 안 된다. 스크린샷 위에 덧그리지 말고 `figcaption`에 쓴다. 영상 캡션은 `browser-repro-video`의 규칙대로 화면 밖 띠에 둔다. 캡션의 숫자는 화면에서 눈으로 셀 수 있는 것과 같아야 한다.
- 썸네일은 가로·세로 원본 비율과 관계없이 동일한 `16/10` 프레임에 `object-fit:contain`으로 넣는다. 같은 폭의 그리드에서는 높이가 같고 이미지 전체가 잘리지 않으며, 자세한 내용은 클릭해서 원본을 크게 본다.
- 템플릿의 이미지 보기용 `<dialog>`·스타일·스크립트를 유지한다. `main` 안의 `figure img`는 클릭 또는 Enter·Space로 크게 열리고, 버튼 또는 좌우 방향키로 보고서 순서대로 이동한다. 첫 이미지의 이전 버튼과 마지막 이미지의 다음 버튼은 비활성화하며 순환하지 않는다. 닫기 버튼·Esc·바깥 배경 클릭으로 닫으면 열었던 이미지로 키보드 초점이 돌아온다.

## 텍스트 슬라이드

Marp(`@marp-team/marp-cli`)로 Markdown을 HTML 슬라이드 파일 하나로 만든다. 브라우저에서 방향키로 넘긴다. Node만 있으면 되고 `npx`가 처음 실행할 때 내려받는다.

```markdown
---
marp: true
paginate: true
size: 16:9
---

# {{주제}} 요약

- {{요구사항 요약 한 줄씩}}
- 위험도 {{낮음|중간|높음}} — {{이유 한 줄}}

---

# 검토자가 볼 곳

- `{{파일:줄}}` — {{이유}}

![h:400](../screenshots/final/{{NN-설명}}.webp)
```

- 슬라이드 하나에 메시지 하나, 글머리표는 5줄 이내. 문장은 보고서에서 가져와 줄이고, 수치는 보고서 값 그대로 쓴다.
- 스크린샷은 `slides/` 기준 상대 경로(`../screenshots/...`)로 넣는다. Marp가 경로를 그대로 둔다. 영상은 넣지 않고 보고서의 영상 구간으로 안내한다.
- 변환: `npx -y @marp-team/marp-cli@latest "<보고서폴더>/slides/presentation.md" -o "<보고서폴더>/slides/presentation.html"`
- 검수: 같은 명령에 `--images png --allow-local-files -o <스크래치패드>/slides/p.png`를 붙여 슬라이드별 PNG를 뽑아 직접 열어 본다. 글자가 넘치거나 잘린 슬라이드는 나눈다. PNG는 보고서 폴더에 두지 않는다.
