이 스킬은 사용자가 리팩터링 요청을 생성하려 할 때 호출됩니다. 아래 단계를 따르세요. 필요하지 않다고 판단되면 일부 단계는 건너뛰어도 됩니다.

1. 사용자에게 해결하려는 문제에 대한 길고 상세한 설명과 잠재적인 해결 아이디어를 물어보세요.

2. 저장소를 탐색하여 사용자의 주장을 검증하고 코드베이스의 현재 상태를 이해하세요.

3. 다른 옵션을 고려했는지 물어보고, 다른 옵션을 제시하세요.

4. 구현에 대해 사용자를 인터뷰하세요. 매우 상세하고 철저하게 진행하세요.

5. 구현의 정확한 범위를 정하세요. 무엇을 변경할지, 무엇을 변경하지 않을지 결정하세요.

6. 코드베이스에서 이 영역의 테스트 커버리지를 확인하세요. 테스트 커버리지가 충분하지 않다면 사용자에게 테스트 계획을 물어보세요.

7. 구현을 작은 커밋 단위로 분해하세요. 마틴 파울러의 조언을 기억하세요: "각 리팩터링 단계를 가능한 한 작게 만들어, 항상 프로그램이 작동하는 것을 볼 수 있게 하라."

8. 리팩터링 계획으로 GitHub 이슈를 생성하세요. 이슈 설명에는 다음 템플릿을 사용하세요:

<refactor-plan-template>

## 문제 진술

개발자의 관점에서 본, 개발자가 직면한 문제.

## 해결책

개발자의 관점에서 본, 문제의 해결책.

## 커밋

길고 상세한 구현 계획. 계획을 평이한 언어로 작성하고, 구현을 가능한 가장 작은 커밋으로 분해하세요. 각 커밋은 코드베이스를 작동 상태로 유지해야 합니다.

## 결정 문서

내려진 구현 결정 사항의 목록입니다. 다음을 포함할 수 있습니다:

- 구축/수정될 모듈
- 수정될 모듈의 인터페이스
- 개발자의 기술적 명확화
- 아키텍처 결정
- 스키마 변경
- API 계약
- 특정 상호작용

특정 파일 경로나 코드 스니펫을 포함하지 마세요. 매우 빠르게 오래된 정보가 될 수 있습니다.

## 테스트 결정 사항

내려진 테스트 결정 사항 목록입니다. 포함할 내용:

- 좋은 테스트의 조건 설명 (구현 세부사항이 아닌 외부 동작만 테스트)
- 테스트할 모듈
- 테스트의 선례 (코드베이스 내 유사한 유형의 테스트)

## 범위 외

이 리팩터링의 범위에서 제외되는 사항에 대한 설명.

## 추가 참고 사항 (선택)

리팩터링에 대한 추가 참고 사항.
