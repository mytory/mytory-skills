# 버그 진단

어려운 버그를 위한 규율 있는 절차입니다. 단계를 건너뛸 때는 이유를 명시하세요. 코드베이스를 탐색할 때 `GLOSSARY.md`가 있으면 읽고, 수정할 영역의 ADR을 확인하세요.

## 민감 정보 가리기

명령, 출력, 수집 자료를 사용자에게 보여주기 전에 **모든 비밀값을 `<REDACTED>`로 가리세요.** 자격 증명을 출력하지 않도록 환경 변수로 반복 검증 명령을 만드세요. 인증 헤더가 담긴 자료에서는 진단에 필요한 줄만 인용하세요. 가린 출력만으로 진단할 수 없다면 밝히고 사용자에게 물으세요.

## 1단계: 피드백 루프 만들기

**이 단계가 스킬의 핵심입니다.** 바로 이 버그에서 실패하는 빠르고 명확한 합격/실패 신호가 있어야 이분 탐색·가설 검증·계측이 가능합니다. 여기에 충분한 시간을 쓰고 다양한 방법을 시도하세요.

### 루프를 만드는 방법: 대략적인 우선순위

1. 버그 경로에 닿는 **실패하는 테스트**: 단위·통합·E2E.
2. 실행 중인 개발 서버에 보내는 **curl/HTTP 스크립트**.
3. 고정 입력으로 실행하고 표준 출력을 정상 스냅샷과 비교하는 **CLI 명령**.
4. UI를 조작하고 DOM·콘솔·네트워크를 검증하는 **헤드리스 브라우저 스크립트**(Playwright/Puppeteer).
5. **수집한 추적 재생**: 실제 요청·페이로드·이벤트 로그를 저장해 코드 경로에 다시 입력.
6. **일회용 검증 장치**: 서비스 하나와 모의 의존성 등 최소 시스템으로 버그 경로를 함수 호출 한 번에 실행.
7. **속성/퍼즈 반복**: 간헐적으로 출력이 틀리면 무작위 입력 1,000개에서 실패 양상을 탐색.
8. **이분 탐색 장치**: 두 상태(커밋·데이터셋·버전) 사이에서 발생했다면 각 상태의 실행과 검사를 자동화해 `git bisect run`에 사용.
9. **차등 검증**: 같은 입력을 구버전과 신버전 또는 두 설정에서 실행해 출력 비교.
10. **사람 참여형 Bash 스크립트**: 사람이 클릭해야 하는 최후의 수단. `scripts/hitl-loop.template.sh`로 절차와 결과 수집을 구조화.

적절한 피드백 루프를 만들면 해결의 대부분을 이룬 셈입니다.

### 루프 다듬기

루프를 하나의 산출물로 다루세요. 준비 과정 캐시, 무관한 초기화 생략, 테스트 범위 축소로 더 빠르게 만드세요. 단순히 충돌하지 않는지 대신 구체적 증상을 검증하세요. 시간·난수·파일시스템·네트워크를 고정해 결과를 일정하게 만드세요. 30초가 걸리고 간헐적으로 실패하는 루프보다 2초짜리 결정적 루프가 유용합니다.

### 비결정적 버그

목표는 매번 재현하는 것이 아니라 **재현율을 높이는 것**입니다. 유발 동작을 100번 반복하고, 병렬 실행·부하 추가·타이밍 구간 축소·지연 주입을 시도하세요. 재현율 1%보다는 50%가 진단하기 쉽습니다.

### 정말 루프를 만들 수 없을 때

멈추고 시도한 방법을 명시하세요. 사용자에게 (a) 재현 환경 접근, (b) 민감 정보를 가린 자료(HAR·로그·코어 덤프·시각 정보가 담긴 화면 녹화), 또는 (c) 임시 운영 환경 계측 권한을 요청하세요. **루프 없이 가설 단계로 넘어가지 마세요.**

### 완료 기준: 실패를 감지할 수 있는 빠른 루프

이미 한 번 이상 실행한 **명령 하나**(스크립트·테스트·curl 등)와 민감 정보를 가린 결과를 제시할 수 있어야 합니다.

- [ ] **실패 감지 가능**: 실제 버그 경로에서 **사용자가 보고한 정확한 증상**을 검증해 버그가 있으면 실패하고 수정되면 성공합니다. 단순 실행 성공 여부는 부족합니다.
- [ ] **결과가 일정함**: 실행마다 같은 판정이 나오며, 간헐적 버그는 재현율이 높습니다.
- [ ] **빠름**: 몇 분이 아닌 몇 초가 걸립니다.
- [ ] **에이전트가 실행 가능**: 무인 실행합니다. 사람 참여는 `scripts/hitl-loop.template.sh`를 통해서만 받습니다.

이 명령을 만들기 전에 코드를 읽으며 원인 이론을 세우고 있다면 **멈추세요.** 실패 감지 명령 없이는 2단계로 가지 마세요.

## 2단계: 재현하고 최소화하기

루프를 실행해 버그 발생 시 실패하는지 확인하세요.

- [ ] 근처의 다른 문제가 아니라 **사용자가 설명한 실패 양상**이 나타납니다.
- [ ] 여러 번 재현됩니다. 비결정적 버그라면 진단할 만큼 재현율이 높습니다.
- [ ] 정확한 증상(오류 메시지·잘못된 출력·느린 시간)을 기록했습니다.

### 최소화

**여전히 실패하는 가장 작은 사례**로 줄이세요. 입력·호출자·설정·데이터·단계를 한 번에 하나씩 빼고 매번 루프를 재실행하세요. 남은 요소를 하나라도 제거하면 성공할 때까지 줄입니다. 최소 재현은 가설 범위를 좁히고 회귀 테스트가 됩니다. **재현과 최소화가 끝나기 전에는 다음 단계로 가지 마세요.**

## 3단계: 가설 세우기

검증 전에 **우선순위를 정한 가설 3~5개**를 만드세요. 첫 번째 생각에 고착되지 않기 위해서입니다. 각 가설에는 **반증 가능한 예측**이 있어야 합니다.

> 형식: "X가 원인이라면 Y를 바꿀 때 버그가 사라지고/Z를 바꿀 때 더 심해진다."

예측을 말할 수 없다면 버리거나 더 구체화하세요. **검증 전에 목록을 사용자에게 보여주세요.** 최근 변경이나 배제된 원인을 알려줄 수 있습니다. 답을 기다리느라 멈추지는 말고 응답이 없으면 정한 순서대로 진행하세요.

## 4단계: 계측하기

각 탐침을 특정 가설의 예측에 연결하고 **한 번에 변수 하나만 바꾸세요.**

1. 환경에서 지원하면 **디버거/REPL 확인**을 우선합니다. 중단점 하나가 로그 열 개보다 낫습니다.
2. 가설을 구분하는 경계에 **대상 로그**를 추가합니다.
3. 모든 곳에 로그를 찍고 검색하지 마세요.

디버그 로그에는 `[DEBUG-a4f2]` 같은 고유 접두어를 붙여 마지막에 한 번의 검색으로 정리하세요. **성능 문제**에서는 로그보다 기준 측정치(`performance.now()`, 프로파일러, 쿼리 실행 계획)와 이분 탐색을 사용하세요. 먼저 측정하고 수정하세요.

## 5단계: 수정하고 회귀 테스트하기

**적절한 테스트 경계가 있을 때만** 수정 전에 회귀 테스트를 작성하세요. 그 경계에서 실제 호출 지점의 버그 양상을 재현할 수 있어야 합니다. 여러 호출자가 필요한데 하나만 검증하거나 발생 경로를 담지 못하는 단위 테스트는 잘못된 확신을 줍니다.

적절한 경계가 없다면 이를 발견 사항으로 기록하고 현재 구조가 재발 방지를 어렵게 한다고 다음 단계에 알리세요. 경계가 있다면:

1. 최소 재현을 실패하는 테스트로 만듭니다.
2. 실제 실패를 확인합니다. 코드나 자료를 조작해 실패시켰다면 원본과 `diff`하여 조작이 적용됐음을 확인하세요.
3. 수정합니다.
4. 테스트 통과를 확인합니다.
5. 1단계 루프를 최소화하지 않은 원래 사례에도 다시 실행합니다.

## 6단계: 정리하기

- [ ] 원래 재현에서 버그가 더는 발생하지 않음(1단계 루프 재실행)
- [ ] 회귀 테스트 통과(또는 적절한 경계가 없음을 문서화)
- [ ] `[DEBUG-...]` 계측 제거(접두어 검색)
- [ ] 일회용 프로토타입 삭제 또는 명확히 표시된 디버그 위치로 이동
- [ ] 실제 원인으로 밝혀진 가설을 커밋/PR 메시지에 기록
