<what-to-do>

우리가 상호 이해에 도달할 때까지 이 계획의 모든 측면에 대해 저를 집요하게 인터뷰해 주세요. 디자인 트리의 각 분기를 짚어가며, 결정 사항들 간의 의존성을 하나씩 해결해 주세요. 각 질문마다 당신이 권장하는 답변을 함께 제안해 주세요.

질문은 한 번에 하나씩만 하고, 각 질문에 대한 피드백을 받은 후에 계속 진행해 주세요.

코드베이스를 탐색하여 답을 찾을 수 있는 질문이라면, 질문하는 대신 코드베이스를 탐색해 주세요.

</what-to-do>

## 도메인 인식

코드베이스 탐색 중에 기존 문서도 함께 찾아보세요:

### 파일 구조

대부분의 저장소는 단일 컨텍스트:

```
/
├── CONTEXT.md
├── docs/
│   └── adr/
│       ├── 0001-event-sourced-orders.md
│       └── 0002-postgres-for-write-model.md
└── src/
```

루트에 `CONTEXT-MAP.md`가 있으면 저장소에 여러 컨텍스트가 있는 것입니다. 맵은 각 컨텍스트의 위치를 가리킵니다:

```
/
├── CONTEXT-MAP.md
├── docs/
│   └── adr/                          ← 시스템 전역 결정
├── src/
│   ├── ordering/
│   │   ├── CONTEXT.md
│   │   └── docs/adr/                 ← 컨텍스트별 결정
│   └── billing/
│       ├── CONTEXT.md
│       └── docs/adr/
```

파일은 게으르게 생성하세요 — 작성할 내용이 있을 때만. `CONTEXT.md`가 없으면 첫 번째 용어가 정리될 때 생성하세요. `docs/adr/`이 없으면 첫 번째 ADR이 필요할 때 생성하세요.

## 세션 중

### 용어집과 대조

사용자가 `CONTEXT.md`의 기존 언어와 충돌하는 용어를 사용하면 즉시 지적하세요. "당신의 용어집은 '취소'를 X로 정의했는데, 지금은 Y를 의미하는 것 같습니다 — 어느 쪽인가요?"

### 모호한 언어 다듬기

사용자가 모호하거나 과부하된 용어를 사용하면 정확한 공식 용어를 제안하세요. "'계정'이라고 하셨는데 — Customer를 의미하나요, User를 의미하나요? 둘은 다른 개념입니다."

### 구체적 시나리오 논의

도메인 관계가 논의될 때, 구체적인 시나리오로 스트레스 테스트하세요. 엣지 케이스를 탐색하고 개념 간 경계를 정확히 하도록 강제하는 시나리오를 만들어내세요.

### 코드와 상호 참조

사용자가 어떤 것이 어떻게 작동한다고 말하면, 코드가 동의하는지 확인하세요. 모순을 발견하면 표면화하세요: "코드에서는 전체 Order를 취소하는데, 방금 부분 취소가 가능하다고 하셨습니다 — 어느 쪽이 맞나요?"

### CONTEXT.md 즉시 업데이트

용어가 정리되면 바로 `CONTEXT.md`를 업데이트하세요. 모아두지 마세요 — 발생하는 대로 캡처하세요. [CONTEXT-FORMAT.md](./CONTEXT-FORMAT.md)의 형식을 사용하세요.

`CONTEXT.md`는 구현 세부사항이 전혀 없어야 합니다. `CONTEXT.md`를 명세, 메모장, 구현 결정 저장소로 취급하지 마세요. 오직 용어집입니다.

### ADR은 절제 있게 제안

다음 세 가지가 모두 참일 때만 ADR 생성을 제안하세요:

1. **되돌리기 어려움** — 나중에 마음을 바꾸는 비용이 의미 있음
2. **맥락 없이 의외임** — 미래의 독자가 "왜 이렇게 했지?"라고 궁금해할 것
3. **실제 트레이드오프의 결과** — 진정한 대안이 있었고 특정 이유로 하나를 선택함

셋 중 하나라도 빠지면 ADR은 건너뛰세요. [ADR-FORMAT.md](./ADR-FORMAT.md)의 형식을 사용하세요.
