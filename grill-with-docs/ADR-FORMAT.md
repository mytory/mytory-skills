# ADR 형식

ADR은 `docs/adr/`에 위치하며 순차적 번호를 사용합니다: `0001-slug.md`, `0002-slug.md` 등.

`docs/adr/` 디렉터리는 첫 번째 ADR이 필요할 때만 게으르게 생성하세요.

## 템플릿

```md
# {결정의 짧은 제목}

{1-3문장: 맥락, 무엇을 결정했는지, 그리고 그 이유.}
```

이게 전부입니다. ADR은 한 문단이어도 됩니다. 가치는 결정이 _내려졌다는 것_과 _왜_ 내려졌는지를 기록하는 데 있습니다 — 섹션을 채우는 것이 아닙니다.

## 선택적 섹션

진정한 가치를 더할 때만 포함하세요. 대부분의 ADR에는 필요하지 않습니다.

- **Status** 프론트매터 (`proposed | accepted | deprecated | superseded by ADR-NNNN`) — 결정이 재검토될 때 유용
- **Considered Options** — 거부된 대안이 기억할 가치가 있을 때만
- **Consequences** — 명백하지 않은 하류 효과를 지적해야 할 때만

## 번호 매기기

`docs/adr/`에서 가장 높은 기존 번호를 스캔하고 1씩 증가.

## ADR을 제안하는 시기

다음 세 가지가 모두 참이어야 합니다:

1. **되돌리기 어려움** — 나중에 마음을 바꾸는 비용이 의미 있음
2. **맥락 없이 의외임** — 미래의 독자가 코드를 보고 "도대체 왜 이렇게 했지?"라고 궁금해할 것
3. **실제 트레이드오프의 결과** — 진정한 대안이 있었고 특정 이유로 하나를 선택함

결정이 되돌리기 쉬우면 건너뛰세요 — 그냥 되돌리면 됩니다. 의외가 아니면 아무도 궁금해하지 않을 것입니다. 실제 대안이 없었다면 "당연한 것을 했다" 외에 기록할 것이 없습니다.

### 자격을 갖추는 것

- **아키텍처 형태.** "모노레포를 사용합니다." "쓰기 모델은 이벤트 소싱, 읽기 모델은 Postgres에 투영됩니다."
- **컨텍스트 간 통합 패턴.** "Ordering과 Billing은 동기 HTTP가 아닌 도메인 이벤트로 통신합니다."
- **락인을 수반하는 기술 선택.** 데이터베이스, 메시지 버스, 인증 제공자, 배포 대상. 모든 라이브러리가 아니라 — 교체하는 데 한 분기가 걸릴 만한 것들만.
- **경계와 범위 결정.** "고객 데이터는 Customer 컨텍스트가 소유합니다; 다른 컨텍스트는 ID로만 참조합니다." 명시적인 '아니오'도 '예'만큼 가치 있습니다.
- **당연한 경로에서의 의도적 이탈.** "ORM 대신 수동 SQL을 사용하는 이유는 X 때문입니다." 합리적인 독자가 반대를 가정할 만한 모든 것. 이것들은 다음 엔지니어가 의도적이었던 무언가를 "고치는" 것을 막습니다.
- **코드에서 보이지 않는 제약.** "규정 준수 요구사항 때문에 AWS를 사용할 수 없습니다." "파트너 API 계약 때문에 응답 시간이 200ms 미만이어야 합니다."
- **거부가 명백하지 않을 때의 거부된 대안.** GraphQL을 고려했지만 미묘한 이유로 REST를 선택했다면 기록하세요 — 그렇지 않으면 누군가 6개월 후에 다시 GraphQL을 제안할 것입니다.
