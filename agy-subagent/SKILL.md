하네스 내장 서브에이전트 도구로는 agy를 부를 수 없다. `scripts/run.sh`를 셸 명령으로 백그라운드 실행한다. 메인은 **지휘자**다. 요구를 해석하고 명세를 쓰고 결과를 판정한다. 일은 agy가 한다.

## 절차

### 1. 나눈다

| agy에 넘긴다 | 메인에 남긴다 |
|---|---|
| 구현, 테스트 작성·실행, 문서 갱신 | 요구 해석, 설계·권한 판단, 사용자와의 대화 |
| 조사·집계, 로그 분석 | 명세 작성, 리뷰 지적의 수용 여부 |
| 읽기 전용 리뷰(`plan` 모드) | 병합·푸시, 공유 자원(메인 체크아웃·메인 DB) 변경 |

완료 기준: 메인에 남은 일이 판단과 확인뿐이다.

### 2. 작업 공간을 따로 준다

agy 하나에 작업 폴더 하나다. 병렬로 돌리면 각자 git 워크트리, 전용 DB 복제본, 서버 포트를 준다. 준비(워크트리 생성, DB 복사, 서버 실행)는 메인이 하고 명세에 적는다.

병렬 작업이 같은 파일을 고칠 것 같으면 **파일 소유권**을 나눈다. 명세마다 "이 파일들은 다른 작업이 고치므로 손대지 않는다"를 목록으로 적고, 겹치는 일은 앞 작업이 병합된 뒤의 다음 단계로 미룬다. 새 코드는 새 파일에 두게 하고, 공용 파일에는 연결 한 줄만 허용한다.

완료 기준: 두 작업의 고칠 파일 목록이 겹치지 않는다(겹치는 파일은 명시한 한두 줄뿐).

### 3. 명세를 파일로 쓴다

명세에 적는 사실은 메인이 원본에서 직접 확인한 것이어야 한다. agy는 프로젝트 규칙 파일(`AGENTS.md` 등)을 스스로 읽지만, 읽으라고 명세 첫머리에 적는다.

명세에 넣는 것:

- 역할("너는 구현 담당, 지휘·리뷰는 다른 에이전트")과 작업 폴더, 건드리면 안 되는 경로·DB
- 사용자 요청 원문 요지와, 메인이 정한 해석·범위(해석은 해석이라고 표시)
- 먼저 읽을 기존 코드와 문서
- 완료 기준이 되는 테스트와 실행 명령, 실행 환경(주소, CLI에 붙일 경로 인자, 계정 만드는 법)
- 커밋 규칙(메시지 형식, 공동 작성자 줄)과 "푸시·병합하지 않는다"
- 같은 실패가 반복될 때 멈출 횟수
- 보고 형식: 커밋 목록, 설계 요약, 테스트별 명령과 결과, 측정값, 못 한 것과 이유, 남은 위험. 추정은 추정이라고 쓰게 한다.

완료 기준: agy가 되묻지 않고 끝낼 수 있고, 결과가 맞는지 메인이 명령 몇 개로 판정할 수 있다.

### 4. 모델과 모드를 고른다

모델 목록은 `agy models`로 본다. 사용자가 고른 모델을 우선한다. 정하지 않았으면 구현은 최신 고성능 계열의 High, 읽기 전용 리뷰는 같은 계열의 Medium 이상, 단순 반복 작업은 Flash 계열로 시작한다. 모델의 실력은 테스트와 독립 리뷰 결과로 판단하고, 모델에 대해 모르는 것은 모른다고 말한다. `agy changelog`에 모델 추가 시점과 구성(예: Orchestrator는 계획 모델과 실행 모델의 조합)이 나온다.

| 모드 | 쓰는 곳 |
|---|---|
| `auto` | 구현. 파일 편집과 명령 실행을 agy의 Auto 검토에 맡긴다 |
| `accept-edits` | 파일 편집만 자동 승인하고 명령은 묻게 할 때 |
| `plan` | 읽기 전용 리뷰·조사 |

`--dangerously-skip-permissions`는 사용자가 명시적으로 허락했을 때만 쓴다.

### 5. 백그라운드로 실행한다

```sh
~/.agents/skills/agy-subagent/scripts/run.sh <작업폴더> <명세.md> <결과.json> [모델] [모드] [대화ID]
```

셸 도구의 백그라운드 실행(Claude Code는 `run_in_background: true`)으로 호출하고 완료 알림을 기다린다. 명세가 있는 폴더는 `--add-dir`로 함께 열리므로, 스크린샷·임시 파일 저장 위치를 그 폴더 아래로 지정할 수 있다. 결과 JSON 옆에 `.log`(agy 로그)와 `.stderr`가 남는다.

오래 걸리는 작업은 진행을 감시한다. 작업 폴더의 새 커밋, 로그 크기가 오래 그대로인 상태, 프로세스 종료를 이벤트로 받는다(Claude Code는 Monitor 도구). 상태 확인에 메인 턴을 쓰지 않는다.

`run.sh`는 `conversation_id`, `status`, 걸린 시간, 턴 수, 토큰, 최종 보고를 출력한다. `conversation_id`는 후속 수정에 쓰므로 기록해 둔다.

완료 기준: `status`가 `SUCCESS`이고 최종 보고가 명세의 보고 형식을 갖췄다. 아니면 6단계로 가지 말고 로그에서 원인을 확인한다.

### 6. 직접 확인한다

최종 보고는 주장일 뿐이다. 한 메시지 안에서 묶어 확인한다.

- `git log`·`git diff --stat 기준..HEAD`로 커밋과 범위 밖 변경이 없는지 본다. 소유권을 나눴으면 금지한 파일이 diff에 없는지 본다.
- 보고한 테스트를 메인이 다시 실행하거나, 실행 기록의 종료 코드와 수치를 읽는다.
- 코드 판단은 독립 리뷰에 맡긴다. 리뷰어는 코드를 쓴 agy가 아닌 다른 에이전트로 고른다.

완료 기준: 보고의 수치를 메인이 다른 경로로 한 번 확인했다.

### 7. 고칠 것을 넘긴다

| 상황 | 방법 |
|---|---|
| 같은 작업의 후속 수정·리뷰 지적 반영 | 같은 `conversation_id`로 이어서 시킨다(`run.sh`의 6번째 인자). 지적은 묶어서 한 번에 넘긴다 |
| 앞 작업 병합 뒤의 다음 단계 | 브랜치를 새 기준 위로 옮긴 뒤 같은 대화로 이어 시키거나, 컨텍스트가 크면 새 대화에 필요한 경로를 다 적는다 |
| 같은 실패가 3회 반복 | 넘기기를 멈추고 메인이 원인을 판단한다. 5회면 실패 보고서를 쓴다 |
| 사용량·크레딧 한도로 멈춤 | 재시도하지 말고 사용자에게 알린다. 멈춘 작업은 산출물 위치와 남은 일을 적어 둔다 |
