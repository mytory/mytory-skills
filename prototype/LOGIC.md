# 로직 프로토타입

사용자가 상태 모델을 직접 조작할 수 있는 작은 대화형 터미널 앱. **비즈니스 로직, 상태 전환, 데이터 형태**에 관한 질문일 때 사용 — 종이 위에서는 합리적으로 보이지만 실제 케이스로 시험해야만 잘못됐다고 느껴지는 종류의 것.

## 이 형태가 적합한 경우

- "이 상태 머신이 X 다음 Y라는 엣지 케이스를 처리하는지 모르겠어."
- "이 데이터 모델이 실제로 ...인 경우를 표현할 수 있나?"
- "작성하기 전에 API가 어떻게 생겨야 할지 감을 잡고 싶어."
- 사용자가 **버튼을 누르고 상태 변화를 지켜보고 싶은** 모든 경우.

질문이 "이게 어떻게 보여야 하나"라면 — 잘못된 브랜치. [UI.md](UI.md) 사용.

## 절차

### 1. 질문 명시

코드 작성 전에 어떤 상태 모델과 어떤 질문을 프로토타입하는지 기록. 프로토타입의 README나 파일 상단 주석에 한 문단으로. 잘못된 질문에 답하는 로직 프로토타입은 순수 낭비 — 질문을 명시적으로 만들어 나중에 확인할 수 있게 하기, 사용자가 지금 보고 있든 나중에 AFK로 돌아오든.

### 2. 언어 선택

호스트 프로젝트가 사용하는 것 사용. 프로젝트에 명백한 런타임이 없으면(예: 문서 저장소), 물어보기.

도구에 프로젝트의 기존 관례 맞추기 — 프로토타입만을 위해 새 패키지 매니저나 런타임 추가하지 말기.

### 3. 로직을 이식 가능한 모듈로 분리

실제 로직 — 질문에 답하는 부분 — 을 나중에 실제 코드베이스로 들어 올려 옮길 수 있는 작고 순수한 인터페이스 뒤에 두기. 주변 TUI는 일회용; 로직 모듈은 그렇지 않아야 함.

올바른 형태는 질문에 따라 다름:

- **순수 리듀서** — `(state, action) => state`. 액션이 이산 이벤트이고 상태가 단일 값일 때 적합.
- **상태 머신** — 명시적 상태와 전환. "지금 어떤 액션이 허용되는가"가 질문의 일부일 때 적합.
- **순수 데이터 타입에 대한 작은 순수 함수 집합** — 암시적 현재 상태가 없을 때 적합 — 그냥 변환.
- **명확한 메서드 표면을 가진 클래스나 모듈** — 로직이 진정으로 지속적인 내부 상태를 소유할 때.

질문되는 내용에 가장 잘 맞는 형태를 선택하고, TUI에 연결하기 가장 쉬운 형태를 선택하지 말 것. 순수하게 유지: I/O 금지, 터미널 코드 금지, 제어 흐름을 위한 `console.log` 금지. TUI가 이를 임포트하고 호출; 반대 방향은 없음.

이것이 프로토타입을 수명 이상으로 유용하게 만드는 것. 질문이 답변되면, 검증된 리듀서 / 머신 / 함수 집합을 실제 모듈로 들어 올릴 수 있음 — TUI 셸은 삭제.

### 4. 상태를 노출하는 가장 작은 TUI 구축

**경량 TUI**로 구축 — 매 틱마다 화면 지우고(`console.clear()` / `print("\033[2J\033[H")` / 동등물) 전체 프레임 다시 렌더링. 사용자는 계속 늘어나는 스크롤백이 아닌 항상 하나의 안정적인 뷰를 봐야 함.

각 프레임은 두 부분으로, 이 순서대로:

1. **현재 상태**, 보기 좋게 출력되고 diff 친화적으로 (필드당 한 줄, 또는 포맷된 JSON). 필드명이나 섹션 헤더는 **볼드**, 덜 중요한 컨텍스트(타임스탬프, ID, 파생 값)는 딤(dim). 네이티브 ANSI 이스케이프 코드 사용 가능 — `\x1b[1m` 볼드, `\x1b[2m` 딤, `\x1b[0m` 리셋. 프로젝트에 이미 있지 않은 한 스타일링 라이브러리 불필요.
2. **키보드 단축키**, 하단에 나열: `[a] 사용자 추가  [d] 사용자 삭제  [t] 시계 틱  [q] 종료`. 키는 볼드, 설명은 딤, 또는 반대 — 깔끔하게 읽히는 대로.

동작:

1. **상태 초기화** — 단일 인메모리 객체/구조체. 시작 시 첫 프레임 렌더링.
2. **한 번에 한 키 입력(또는 한 줄)** 읽고, 상태를 변경하는 핸들러로 디스패치.
3. 모든 액션 후 전체 프레임 **다시 렌더링** — 추가하지 말고 교체.
4. **종료까지 루프.**

전체 프레임이 한 화면에 맞아야 함.

### 5. 하나의 명령으로 실행 가능하게

프로젝트의 기존 작업 실행기에 스크립트 추가(`package.json` scripts, `Makefile`, `justfile`, `pyproject.toml`). 사용자는 `pnpm run <prototype-name>` 또는 동등물을 실행해야 함 — 경로를 기억할 필요 절대 없음.

호스트 프로젝트에 작업 실행기가 없으면 프로토타입 README 상단에 명령어를 두기.

### 6. 전달

사용자에게 실행 명령어 제공. 그들은 직접 조작할 것; 흥미로운 순간은 "잠깐, 그게 가능하면 안 되는데" 또는 "어, X가 다를 줄 알았는데"라고 말할 때 — 그것들이 _아이디어_ 속의 버그, 즉 전체 요점. 새 액션 추가를 원하면 추가. 프로토타입은 진화함.

### 7. 답변 캡처

프로토타입이 역할을 다하면, 질문에 대한 답변이 유일하게 보존할 가치가 있는 것. 사용자가 있으면 무엇을 배웠는지 물어보기. 없으면 프로토타입 옆에 `NOTES.md`를 남겨, 프로토타입이 삭제되기 전에 답변을 채울 수 있게 (또는 세션을 지켜봤다면 당신이 채움).

## 안티패턴

- **테스트 추가하지 말기.** 테스트가 필요한 프로토타입은 더 이상 프로토타입이 아님.
- **실제 데이터베이스에 연결하지 말기.** 질문이 특별히 지속성에 관한 것이 아니면 인메모리 저장소 사용.
- **일반화하지 말기.** "나중에 X를 지원하려면 어쩌지" 금지. 프로토타입은 하나의 질문에 답함.
- **로직과 TUI를 섞지 말기.** 리듀서/상태 머신이 `console.log`, 프롬프트, 터미널 이스케이프 코드를 참조하면 더 이상 이식 불가능. TUI를 순수 모듈 위의 얇은 셸로 유지.
- **TUI 셸을 프로덕션에 배포하지 말기.** 셸은 터미널에서 수동으로 조작하도록 최적화됨. 그 뒤의 로직 모듈이 보존할 가치가 있는 부분.
