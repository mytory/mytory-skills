# UI 프로토타입

하나의 라우트에 **근본적으로 다른 여러 UI 변형**을 생성하고, 플로팅 하단 바로 전환 가능하게. 사용자가 브라우저에서 변형을 넘겨보며 하나를 고르거나(또는 각각에서 일부를 가져오고), 나머지는 버림.

질문이 무엇이 어떻게 보이는지가 아닌 로직/상태라면 — 잘못된 브랜치. [LOGIC.md](LOGIC.md) 사용.

## 이 형태가 적합한 경우

- "이 페이지가 어떻게 보여야 하나?"
- "커밋하기 전에 이 대시보드의 몇 가지 옵션을 보고 싶어."
- "설정 화면에 다른 레이아웃 시도해 봐."
- 사용자가 머릿속의 세 가지 모호한 목업 사이에서 하루를 보낼 모든 경우.

## 두 가지 하위 형태 — 하위 형태 A를 강력히 선호

UI 프로토타입은 **앱의 나머지와 맞닿아 있을 때** 판단하기 훨씬 쉬움 — 실제 헤더, 실제 사이드바, 실제 데이터, 실제 밀도. 단독 일회용 라우트는 진공 상태: 모든 변형이 따로 떼어놓고 보면 괜찮아 보임. 변형을 호스팅할 그럴듯한 기존 페이지가 있을 때마다 하위 형태 A를 기본값으로. 프로토타입이 진정으로 가까운 집이 없을 때만 하위 형태 B 사용.

### 하위 형태 A — 기존 페이지 조정 (선호)

라우트가 이미 존재. 변형은 `?variant=` URL 검색 파라미터로 게이트되어 **동일한 라우트**에서 렌더링. 기존 데이터 페칭, 파라미터, 인증은 모두 유지 — 렌더링만 교체. 특별한 이유가 없는 한 이것이 기본값.

프로토타입이 아직 페이지가 없지만 *자연스럽게 하나 안에 들어갈*(대시보드의 새 섹션, 설정 화면의 새 카드, 기존 흐름의 새 단계) 것이라면 — 여전히 하위 형태 A. 호스트 페이지 안에 변형 마운트.

### 하위 형태 B — 새 페이지 (최후의 수단)

프로토타입 대상이 진정으로 안에 들어갈 기존 페이지가 없을 때만 사용 — 예: 완전히 새로운 최상위 표면, 또는 어디에도 합리적으로 임베드할 수 없는 흐름.

프로젝트가 이미 사용하는 라우팅 관례를 따라 **일회용 라우트** 생성 — 새 최상위 구조 발명 금지. 프로토타입임이 분명하도록 이름 짓기 (예: 경로나 파일명에 `prototype` 단어 포함). 동일한 `?variant=` 패턴.

하위 형태 B에 커밋하기 전에 정신 차리기: 정말로 임베드할 기존 페이지가 없는가? 빈 라우트는 채워진 라우트가 드러낼 디자인 문제를 숨김.

두 하위 형태 모두 플로팅 하단 바는 동일.

## 절차

### 1. 질문 명시하고 N 선택

기본값은 **3개 변형**. 5개 초과는 근본적으로 달라지기를 멈추고 노이즈가 됨 — 상한 거기.

계획을 한 줄로 기록, 프로토타입 위치나 파일 상단 주석에:

> "설정 페이지의 세 가지 변형, `?variant=`로 전환 가능, 기존 `/settings` 라우트에서."

사용자가 반대하든 말든 작동.

### 2. 근본적으로 다른 변형 생성

각 변형 초안 작성. 각각에 대해 확인:

- 페이지의 목적과 접근 가능한 데이터.
- 프로젝트의 컴포넌트 라이브러리 / 스타일링 시스템 (TailwindCSS, shadcn, MUI, plain CSS 등).
- 명확한 내보내기 컴포넌트명, 예: `VariantA`, `VariantB`, `VariantC`.

변형은 **구조적으로 달라야** 함 — 다른 레이아웃, 다른 정보 계층, 다른 주요 행동 유도, 단순히 다른 색상이 아님. 약간 조정된 세 개의 카드 그리드는 UI 프로토타입이 아니라 벽지. 두 초안이 너무 비슷해지면 명시적 "카드 그리드 사용 금지" 지침으로 하나 다시 작성.

### 3. 함께 연결

라우트에 단일 전환기 컴포넌트 생성:

```tsx
// 의사 코드 — 프로젝트 프레임워크에 맞게 조정
const variant = searchParams.get('variant') ?? 'A';
return (
  <>
    {variant === 'A' && <VariantA {...data} />}
    {variant === 'B' && <VariantB {...data} />}
    {variant === 'C' && <VariantC {...data} />}
    <PrototypeSwitcher variants={['A','B','C']} current={variant} />
  </>
);
```

하위 형태 A (기존 페이지): 기존 데이터 페칭을 전환기 위에 모두 유지; 변형별로 렌더링된 하위 트리만 변경.

하위 형태 B (새 페이지): `/prototype/<name>` 아래의 일회용 라우트가 동일한 전환기 마운트.

### 4. 플로팅 전환기 구축

화면 하단 중앙의 작은 고정 위치 바, 세 부분:

- **왼쪽 화살표** — 이전 변형으로 순환 (순환 랩어라운드).
- **변형 라벨** — 현재 변형 키와, 변형이 이름을 내보내면 그 이름도 표시. 예: `B — 사이드바 레이아웃`.
- **오른쪽 화살표** — 앞으로 순환 (순환 랩어라운드).

동작:

- 화살표 클릭 시 URL 검색 파라미터 업데이트 (프레임워크 라우터 사용 — Next에서는 `router.replace`, React Router에서는 `navigate` 등)하여 변형이 공유 가능하고 리로드 안정적이게.
- 키보드: `←`와 `→` 화살표 키도 순환. `<input>`, `<textarea>`, `[contenteditable]`이 포커스되었을 때는 화살표 키 가로채지 말 것.
- 페이지와 시각적으로 구별되게 (예: 고대비 필, 미묘한 그림자) 평가 대상 디자인의 일부가 아님을 분명히.
- 프로덕션 빌드에서 숨김 — `process.env.NODE_ENV !== 'production'` 또는 동등한 검사로 게이트하여, 실수로 병합된 프로토타입이 사용자에게 바를 배포할 수 없게.

전환기를 단일 공유 컴포넌트에 두어 두 하위 형태 모두 재사용 가능하게. 프로젝트에서 공유 UI가 있는 곳에 배치.

### 5. 전달

URL(과 `?variant=` 키) 표면화. 사용자는 접근할 때마다 넘겨볼 것. 흥미로운 피드백은 보통 **"B의 헤더와 C의 사이드바가 좋겠어"** — 그게 그들이 실제로 원하는 디자인.

### 6. 답변 캡처 및 정리

변형이 승리하면, 어느 것이고 왜인지 기록 (커밋 메시지, ADR, 이슈, 또는 AFK 실행 중이고 사용자가 아직 응답하지 않았으면 프로토타입 옆의 `NOTES.md`). 그런 다음:

- **하위 형태 A** — 패배한 변형과 전환기 삭제; 승자를 기존 페이지에 통합.
- **하위 형태 B** — 승리한 변형을 실제 라우트로 승격, 일회용 라우트와 전환기 삭제.

변형 컴포넌트나 전환기를 방치하지 말기. 빨리 썩고 다음 독자를 혼란스럽게 함.

## 안티패턴

- **색상이나 카피만 다른 변형.** 그건 조정이지 프로토타입이 아님. 진짜 변형은 구조에 대해 의견이 다름.
- **변형 간 코드를 너무 많이 공유.** 공유 `<Header>`는 괜찮음; 공유 `<Layout>`은 요점을 무력화. 각 변형은 레이아웃을 버릴 자유가 있어야 함.
- **변형을 실제 뮤테이션에 연결.** 읽기 전용 프로토타입으로 충분. 변형이 뮤테이션이 필요하면 스텁을 가리키게 — 질문은 "이게 어떻게 보여야 하나"이지 "백엔드가 작동하나"가 아님.
- **프로토타입을 직접 프로덕션으로 승격.** 변형 코드는 프로토타입 제약 하에 작성됨 (테스트 없음, 최소 오류 처리). 통합할 때 제대로 다시 작성.
