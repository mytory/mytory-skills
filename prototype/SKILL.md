# 프로토타입

프로토타입은 **질문에 답하는 일회용 코드**입니다. 질문이 형태를 결정합니다.

## 브랜치 선택

어떤 질문에 답하고 있는지 식별 — 사용자 프롬프트, 주변 코드, 또는 사용자에게 물어서:

- **"이 로직 / 상태 모델이 맞는 느낌인가?"** → [LOGIC.md](LOGIC.md). 종이 위에서 추론하기 어려운 케이스를 통해 상태 머신을 밀어붙이는 작은 대화형 터미널 앱 구축.
- **"이게 어떻게 보여야 하나?"** → [UI.md](UI.md). URL 검색 파라미터와 플로팅 하단 바로 전환 가능한, 하나의 라우트에 근본적으로 다른 여러 UI 변형 생성.

두 브랜치는 매우 다른 결과물을 생성 — 이것을 잘못 선택하면 프로토타입 전체가 낭비. 질문이 진정으로 모호하고 사용자에게 연락할 수 없으면, 주변 코드와 더 잘 맞는 브랜치를 기본값으로 선택(백엔드 모듈 → 로직; 페이지나 컴포넌트 → UI)하고 프로토타입 상단에 가정을 명시.

## 양쪽에 적용되는 규칙

1. **첫날부터 일회용이며, 명확히 표시.** 프로토타입 코드를 실제로 사용될 위치 가까이에 배치(프로토타입 중인 모듈이나 페이지 옆)하여 컨텍스트가 분명하게 — 하지만 일반 독자가 프로덕션이 아닌 프로토타입임을 알 수 있도록 이름 짓기. 일회용 UI 라우트의 경우, 프로젝트가 이미 사용하는 라우팅 관례를 따르고; 새 최상위 구조를 발명하지 말 것.
2. **하나의 명령으로 실행.** 프로젝트의 기존 작업 실행기가 지원하는 것 — `pnpm <name>`, `python <path>`, `bun <path>` 등. 사용자가 생각 없이 시작할 수 있어야 함.
3. **기본적으로 지속성 없음.** 상태는 메모리에 존재. 지속성은 프로토타입이 _확인하는_ 대상이지 의존해야 하는 대상이 아님. 질문이 명시적으로 데이터베이스를 포함하면, 명확한 "PROTOTYPE — 지워도 됨" 이름으로 스크래치 DB나 로컬 파일에 접근.
4. **다듬기 건너뛰기.** 테스트 없음, 프로토타입을 _실행 가능하게_ 만드는 것 이상의 오류 처리 없음, 추상화 없음. 요점은 빠르게 배우고 그 다음 삭제하는 것.
5. **상태 표면화.** 모든 액션 후(로직) 또는 모든 변형 전환 시(UI), 전체 관련 상태를 출력하거나 렌더링하여 사용자가 무엇이 변경되었는지 볼 수 있게.
6. **완료 시 삭제 또는 흡수.** 프로토타입이 질문에 답했으면 삭제하거나 검증된 결정을 실제 코드에 통합 — 저장소에 썩게 두지 말 것.

## 완료 시

프로토타입에서 유일하게 보존할 가치가 있는 것은 _답변_입니다. 답변한 질문과 함께 내구성 있는 곳(커밋 메시지, ADR, 이슈, 프로토타입 옆의 `NOTES.md`)에 캡처하세요. 사용자가 있으면 빠른 대화로 캡처; 없으면 플레이스홀더를 남겨 그들(또는 당신, 다음 패스에서)이 프로토타입 삭제 전에 평결을 채울 수 있게.
