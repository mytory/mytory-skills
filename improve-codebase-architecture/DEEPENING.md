# 심화

의존성을 고려하여 얕은 모듈 군집을 안전하게 심화하는 방법. [LANGUAGE.md](LANGUAGE.md)의 어휘 — **모듈**, **인터페이스**, **이음새**, **어댑터** — 를 가정.

## 의존성 카테고리

심화 후보 평가 시 의존성 분류. 카테고리가 심화된 모듈이 이음새를 따라 어떻게 테스트될지 결정.

### 1. 인프로세스

순수 계산, 인메모리 상태, I/O 없음. 항상 심화 가능 — 모듈 병합하고 새 인터페이스로 직접 테스트. 어댑터 불필요.

### 2. 로컬 대체 가능

로컬 테스트 대체재가 있는 의존성 (Postgres용 PGLite, 인메모리 파일 시스템). 대체재가 존재하면 심화 가능. 심화된 모듈은 테스트 스위트에서 대체재 실행으로 테스트. 이음새는 내부; 모듈의 외부 인터페이스에 포트 없음.

### 3. 원격이지만 소유 (Ports & Adapters)

네트워크 경계 너머의 자체 서비스 (마이크로서비스, 내부 API). 이음새에 **포트**(인터페이스) 정의. 깊은 모듈이 로직 소유; 전송은 **어댑터**로 주입. 테스트는 인메모리 어댑터 사용. 프로덕션은 HTTP/gRPC/큐 어댑터 사용.

권장 형태: *"이음새에 포트 정의, 프로덕션용 HTTP 어댑터와 테스트용 인메모리 어댑터 구현, 네트워크 너머에 배포되어도 로직이 하나의 깊은 모듈에 있도록."*

### 4. 진정한 외부 (Mock)

당신이 통제하지 않는 서드파티 서비스 (Stripe, Twilio 등). 심화된 모듈은 외부 의존성을 주입 포트로 받음; 테스트는 모의 어댑터 제공.

## 이음새 규율

- **어댑터 하나는 가상 이음새를 의미. 어댑터 둘은 실제 이음새를 의미.** 최소 두 개의 어댑터가 정당화되지 않으면(일반적으로 프로덕션 + 테스트) 포트 도입 금지. 단일 어댑터 이음새는 그냥 간접 참조.
- **내부 이음새 vs 외부 이음새.** 깊은 모듈은 인터페이스의 외부 이음새뿐 아니라 내부 이음새(구현에 비공개, 자체 테스트에서 사용)도 가질 수 있음. 테스트가 사용한다고 해서 내부 이음새를 인터페이스로 노출하지 말 것.

## 테스트 전략: 교체, 계층화 금지

- 얕은 모듈의 기존 유닛 테스트는 심화된 모듈 인터페이스의 테스트가 존재하면 폐기물 — 삭제.
- 심화된 모듈의 인터페이스에 새 테스트 작성. **인터페이스는 테스트 표면**.
- 테스트는 내부 상태가 아닌 인터페이스를 통한 관찰 가능한 결과로 단언.
- 테스트는 내부 리팩터에서 살아남아야 함 — 구현이 아닌 동작을 설명. 구현 변경 시 테스트가 바뀌어야 한다면 인터페이스 너머를 테스트하고 있는 것.
