# 인터페이스 설계

선택된 심화 후보에 대해 사용자가 대체 인터페이스를 탐색하고 싶을 때 이 병렬 하위 에이전트 패턴 사용. "두 번 설계하기" (Ousterhout) 기반 — 첫 아이디어가 최고일 가능성 낮음.

[LANGUAGE.md](LANGUAGE.md)의 어휘 — **모듈**, **인터페이스**, **이음새**, **어댑터**, **레버리지** — 사용.

## 절차

### 1. 문제 공간 프레이밍

하위 에이전트 생성 전, 선택된 후보의 문제 공간에 대한 사용자 대상 설명 작성:

- 새 인터페이스가 만족해야 할 제약
- 의존할 의존성과 해당 카테고리 ([DEEPENING.md](DEEPENING.md) 참조)
- 제약을 구체화하는 대략적인 설명 코드 스케치 — 제안이 아니라 제약을 구체화하는 방식

사용자에게 보여준 후 즉시 2단계 진행. 하위 에이전트가 병렬 작업하는 동안 사용자가 읽고 생각.

### 2. 하위 에이전트 생성

Agent 도구를 사용해 3개 이상의 하위 에이전트를 병렬로 생성. 각각 심화된 모듈에 대해 **근본적으로 다른** 인터페이스 생산.

각 하위 에이전트에 별도의 기술 브리핑으로 프롬프트 (파일 경로, 결합 세부사항, [DEEPENING.md](DEEPENING.md)의 의존성 카테고리, 이음새 뒤에 무엇이 있는지). 브리핑은 1단계의 사용자 대상 문제 공간 설명과 독립적. 각 에이전트에 다른 설계 제약 부여:

- 에이전트 1: "인터페이스 최소화 — 최대 1-3개 진입점 목표. 진입점당 레버리지 극대화."
- 에이전트 2: "유연성 극대화 — 많은 사용 사례와 확장 지원."
- 에이전트 3: "가장 일반적인 호출자에 최적화 — 기본 케이스를 사소하게."
- 에이전트 4 (해당 시): "이음새 횡단 의존성을 위한 포트 & 어댑터로 설계."

브리핑에 [LANGUAGE.md](LANGUAGE.md) 어휘와 CONTEXT.md 어휘를 모두 포함하여 각 하위 에이전트가 아키텍처 언어와 프로젝트의 도메인 언어로 일관되게 명명하도록.

각 하위 에이전트 출력:

1. 인터페이스 (타입, 메서드, 매개변수 — 불변식, 순서, 오류 모드 포함)
2. 호출자 사용 방식을 보여주는 사용 예시
3. 구현이 이음새 뒤에 숨기는 것
4. 의존성 전략과 어댑터 ([DEEPENING.md](DEEPENING.md) 참조)
5. 트레이드오프 — 레버리지가 높은 곳, 얇은 곳

### 3. 제시 및 비교

사용자가 각각을 이해할 수 있도록 설계를 순차적으로 제시한 후 산문으로 비교. **깊이**(인터페이스에서의 레버리지), **지역성**(변경이 집중되는 곳), **이음새 배치**로 대조.

비교 후 자신의 권장 제공: 어떤 설계가 가장 강력하다고 생각하는지와 그 이유. 다른 설계의 요소들이 잘 결합된다면 하이브리드 제안. 주관적이어야 함 — 사용자는 메뉴가 아닌 강력한 평가를 원함.
