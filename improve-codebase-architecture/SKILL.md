# 코드베이스 아키텍처 개선

아키텍처 마찰을 표면화하고 **심화 기회** — 얕은 모듈을 깊은 모듈로 바꾸는 리팩터 — 제안. 목표는 테스트 용이성과 AI 탐색 가능성.

## 용어집

모든 제안에서 이 용어들을 정확히 사용. 일관된 언어가 요점 — "컴포넌트", "서비스", "API", "경계"로 이탈하지 말 것. 전체 정의는 [LANGUAGE.md](LANGUAGE.md) 참조.

- **모듈** — 인터페이스와 구현이 있는 모든 것(함수, 클래스, 패키지, 슬라이스).
- **인터페이스** — 호출자가 모듈을 사용하기 위해 알아야 하는 모든 것: 타입, 불변식, 오류 모드, 순서, 설정. 타입 시그니처만이 아님.
- **구현** — 내부 코드.
- **깊이** — 인터페이스에서의 레버리지: 작은 인터페이스 뒤의 많은 동작. **깊음** = 높은 레버리지. **얕음** = 인터페이스가 구현만큼 복잡.
- **이음새** — 인터페이스가 있는 곳; 제자리 편집 없이 동작을 변경할 수 있는 장소. ("경계" 대신 이것 사용.)
- **어댑터** — 이음새에서 인터페이스를 만족하는 구체적 대상.
- **레버리지** — 호출자가 깊이에서 얻는 것.
- **지역성** — 유지보수자가 깊이에서 얻는 것: 변경, 버그, 지식이 한 곳에 집중.

주요 원칙 (전체 목록은 [LANGUAGE.md](LANGUAGE.md) 참조):

- **삭제 테스트**: 모듈 삭제를 상상. 복잡성이 사라지면 통과용이었음. 복잡성이 N개 호출자에 재등장하면 제 몫을 하고 있었음.
- **인터페이스는 테스트 표면.**
- **어댑터 하나 = 가상 이음새. 어댑터 둘 = 실제 이음새.**

이 스킬은 프로젝트의 도메인 모델에 의해 정보를 얻음. 도메인 언어가 좋은 이음새에 이름을 부여; ADR이 스킬이 재논의하지 말아야 할 결정을 기록.

## 절차

### 1. 탐색

먼저 프로젝트의 도메인 용어집과 다루는 영역의 ADR 읽기.

그런 다음 Agent 도구를 `subagent_type=Explore`로 사용하여 코드베이스 탐색. 경직된 휴리스틱을 따르지 말고 — 유기적으로 탐색하며 마찰을 경험한 곳 기록:

- 한 개념을 이해하는 데 많은 작은 모듈 사이를 오가야 하는 곳은?
- 모듈이 **얕은** 곳은 — 인터페이스가 구현만큼 복잡한 곳?
- 테스트 용이성만을 위해 순수 함수가 추출되었지만, 실제 버그는 호출 방식에 숨어 있는 곳은(**지역성** 없음)?
- 밀접 결합된 모듈이 이음새를 넘어 누수되는 곳은?
- 코드베이스의 어느 부분이 테스트되지 않았거나 현재 인터페이스로 테스트하기 어려운가?

얕다고 의심되는 모든 것에 **삭제 테스트** 적용: 삭제하면 복잡성이 집중될까, 아니면 그냥 이동할까? "예, 집중됨"이 원하는 신호.

### 2. 후보를 HTML 보고서로 제시

저장소에 아무것도 남지 않도록 OS 임시 디렉터리에 자기완결적 HTML 파일 작성. `$TMPDIR`에서 임시 디렉터리 해석, 없으면 `/tmp`(Windows는 `%TEMP%`)로 폴백, `<tmpdir>/architecture-review-<timestamp>.html`에 작성하여 실행마다 새 파일. 사용자에게 열기 — Linux는 `xdg-open <path>`, macOS는 `open <path>`, Windows는 `start <path>` — 절대 경로 알리기.

보고서는 레이아웃과 스타일링에 **CDN을 통한 Tailwind**, 그래프/흐름/시퀀스가 구조를 안정적으로 전달하는 곳에 **CDN을 통한 Mermaid** 사용. Mermaid와 수제 CSS/SVG 비주얼 혼합 — 관계가 그래프 형태일 때(호출 그래프, 의존성, 시퀀스) Mermaid 사용, 더 에디토리얼한 것이 필요할 때(질량 다이어그램, 단면도, 축소 애니메이션) 수제 div/SVG 사용. 각 후보는 **전/후 시각화**를 가짐. 시각적이어야 함.

각 후보는 이전과 동일한 템플릿이지만 카드로 렌더링:

- **파일** — 관련 파일/모듈
- **문제** — 현재 아키텍처가 마찰을 일으키는 이유
- **해결책** — 무엇이 변경될지 평이한 언어 설명
- **이점** — 지역성과 레버리지로 설명, 테스트가 어떻게 개선될지
- **전/후 다이어그램** — 나란히, 수제로 그려서, 얕음과 심화를 보여줌
- **권장 강도** — `강력`, `탐색 가치`, `추측` 중 하나, 배지로 렌더링

**최상위 권장** 섹션으로 보고서 마무리: 어떤 후보를 먼저 다룰지와 그 이유.

**도메인에는 CONTEXT.md 어휘, 아키텍처에는 [LANGUAGE.md](LANGUAGE.md) 어휘 사용.** `CONTEXT.md`가 "Order"를 정의하면 "the Order intake module"이라고 말하기 — "the FooBarHandler"도, "the Order service"도 아님.

**ADR 충돌**: 후보가 기존 ADR과 모순되면, ADR 재검토가 보증될 만큼 마찰이 실제일 때만 표면화. 카드에 명확히 표시 (예: 경고 콜아웃: _"ADR-0007과 모순 — 하지만 ... 때문에 재논의 가치"_). ADR이 금지하는 모든 이론적 리팩터를 나열하지 말기.

전체 HTML 스캐폴드, 다이어그램 패턴, 스타일링 가이드는 [HTML-REPORT.md](HTML-REPORT.md) 참조.

아직 인터페이스 제안하지 말기. 파일 작성 후 사용자에게 물어보기: "이 중 어떤 것을 탐색하고 싶으신가요?"

### 3. 질문 루프

사용자가 후보를 선택하면 질문 대화로 진입. 그들과 디자인 트리 탐색 — 제약, 의존성, 심화된 모듈의 형태, 이음새 뒤에 무엇이 있는지, 어떤 테스트가 살아남는지.

결정이 구체화됨에 따라 인라인으로 부작용 발생:

- **`CONTEXT.md`에 없는 개념을 따서 심화된 모듈 이름 짓기?** `CONTEXT.md`에 용어 추가 — `/grill-with-docs`와 동일한 규율 ([CONTEXT-FORMAT.md](../grill-with-docs/CONTEXT-FORMAT.md) 참조). 없으면 파일을 게으르게 생성.
- **대화 중 모호한 용어 다듬기?** 바로 `CONTEXT.md` 업데이트.
- **사용자가 부하를 견디는 이유로 후보 거부?** ADR 제안, 프레이밍: _"향후 아키텍처 리뷰가 다시 제안하지 않도록 이걸 ADR로 기록할까요?"_ 미래 탐색자가 동일한 것을 다시 제안하지 않기 위해 이유가 실제로 필요할 때만 제안 — 일시적 이유("지금은 가치 없음")와 자명한 것은 건너뛰기. [ADR-FORMAT.md](../grill-with-docs/ADR-FORMAT.md) 참조.
- **심화된 모듈의 대체 인터페이스 탐색 원함?** [INTERFACE-DESIGN.md](INTERFACE-DESIGN.md) 참조.
