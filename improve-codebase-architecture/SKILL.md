# 코드베이스 아키텍처 개선

아키텍처의 마찰을 드러내고 **심화 기회**를 제안하세요. 얕은 모듈을 깊은 모듈로 바꾸는 리팩터링을 찾습니다. 목표는 테스트 용이성과 AI가 코드를 탐색하기 쉬운 구조입니다.

이 명령은 프로젝트의 도메인 모델을 참고하며 공통 설계 어휘를 사용합니다.

- Skill 도구로 "codebase-design"을 호출하여 아키텍처 어휘(**module**, **interface**, **depth**, **seam**, **adapter**, **leverage**, **locality**)와 원칙(삭제 테스트, "interface가 테스트 표면이다", "adapter 하나는 가상의 seam이고 둘은 실제 seam이다")을 가져오세요. 모든 제안에서 이 용어를 정확히 사용하고 "component", "service", "API", "boundary"로 바꾸지 마세요.
- `GLOSSARY.md`의 도메인 용어는 좋은 seam의 이름을 제공하고, `docs/adr/`의 ADR은 이 명령에서 다시 논쟁하지 않을 결정을 기록합니다.

## 절차

### 1. 탐색

**살펴보기 전에 범위를 정하세요. YAGNI.** 모듈을 심화하는 가치는 향후 변경을 쉽게 만드는 데 있으므로 최근 자주 변경된 부분에 더 큰 가중치를 두세요. 살펴볼 곳을 먼저 결정하세요.

- 사용자가 방향(모듈, 하위 시스템, 문제점)을 지정했다면 그곳을 대상으로 하고 아래 추론은 건너뛰세요.
- 그렇지 않다면 충분한 기간의 커밋 기록(`git log --oneline`)을 거슬러 올라가 반복해서 등장하는 파일과 영역을 찾고, 그 경로부터 살펴보세요. 변경이 흩어져 뚜렷한 집중 영역이 없다면 범위를 넓히세요.

먼저 프로젝트의 도메인 용어집(`GLOSSARY.md`)과 대상 영역의 ADR을 읽으세요.

그다음 하위 에이전트가 코드베이스를 살펴보게 하세요. 경직된 휴리스틱 대신 자연스럽게 탐색하며 마찰을 기록하세요.

- 한 개념을 이해하려면 작은 모듈 여러 개를 오가야 하나요?
- **module**이 얕아서 **interface**가 구현만큼 복잡한가요?
- 테스트만을 위해 순수 함수를 추출했지만 실제 버그는 호출 방식에 숨어 있나요(**locality** 부재)?
- 밀접하게 결합된 모듈이 서로의 **seam**을 침범하나요?
- 테스트가 없거나 현재 **interface**를 통해 테스트하기 어려운 영역이 있나요?

얕다고 의심되는 부분에는 **삭제 테스트**를 적용하세요. 그 부분을 삭제하면 복잡성이 한곳에 모이나요, 아니면 단지 다른 곳으로 옮겨가나요? 복잡성이 모인다면 살펴볼 만한 신호입니다.

### 2. 후보를 HTML 보고서로 제시

저장소에 파일이 남지 않도록 운영체제의 임시 디렉터리에 독립 실행형 HTML 파일을 작성하세요. `$TMPDIR`을 사용하고, 없으면 `/tmp`(Windows에서는 `%TEMP%`)을 사용하세요. 매번 새 파일이 되도록 `<tmpdir>/architecture-review-<timestamp>.html`에 저장하세요. 사용자에게 파일을 열어 보여주고(Linux: `xdg-open <path>`, macOS: `open <path>`, Windows: `start <path>`) 절대 경로를 알려주세요.

보고서의 레이아웃과 스타일에는 CDN의 **Tailwind**를, 그래프·흐름·시퀀스가 구조를 명확하게 보여줄 때는 CDN의 **Mermaid**를 사용하세요. Mermaid와 직접 만든 CSS/SVG 시각 자료를 섞으세요. 관계가 그래프 형태라면 Mermaid를, 질량도·단면도·접힘 애니메이션처럼 편집 디자인이 필요한 곳에는 직접 만든 div/SVG를 사용하세요. 각 후보에는 **변경 전/후 시각화**를 넣으세요.

각 후보 카드에는 다음을 포함하세요.

- **파일**: 관련된 파일과 모듈
- **문제**: 현재 아키텍처가 마찰을 일으키는 이유
- **해결책**: 변경할 내용을 일상적인 말로 설명
- **이점**: locality, leverage, 테스트 개선의 관점에서 설명
- **변경 전/후 다이어그램**: 얕은 구조와 심화된 구조를 직접 그려 나란히 표시
- **추천 강도**: `Strong`, `Worth exploring`, `Speculative` 중 하나를 배지로 표시

보고서 끝에는 **최우선 추천** 섹션을 두고 가장 먼저 다룰 후보와 그 이유를 적으세요.

도메인에는 **`GLOSSARY.md`의 용어**, 아키텍처에는 **`/codebase-design`의 어휘**를 사용하세요. `GLOSSARY.md`에 "Order"가 정의되어 있다면 "FooBarHandler"나 "Order service" 대신 "Order intake module"이라고 부르세요.

**ADR과 충돌하는 경우**: 기존 ADR과 상충하는 후보는 실제 마찰이 ADR 재검토를 정당화할 때만 제시하세요. 카드에 _"ADR-0007과 충돌하지만 … 때문에 재검토할 만함"_과 같이 명확히 표시하세요. ADR이 금지하는 이론적 리팩터링을 모두 나열하지 마세요.

전체 HTML 뼈대, 다이어그램 패턴, 스타일 지침은 [HTML-REPORT.md](HTML-REPORT.md)를 참고하세요.

아직 interface를 제안하지 마세요. 파일을 작성한 뒤 사용자에게 "어떤 후보를 더 살펴볼까요?"라고 물으세요.

### 3. 심층 인터뷰

사용자가 후보를 선택하면 Skill 도구로 "grilling"을 호출하고 제약, 의존성, 심화된 모듈의 형태, seam 뒤에 놓일 것, 유지할 테스트를 차례로 검토하세요.

결정이 구체화되면 바로 부수 작업을 수행하세요. Skill 도구로 "domain-modeling"을 호출해 도메인 모델을 최신 상태로 유지하세요.

- **심화된 모듈의 이름이 `GLOSSARY.md`에 없는 개념인가요?** 용어를 추가하세요. 파일이 없으면 그때 만드세요.
- **대화 중 모호한 용어가 명확해졌나요?** 즉시 `GLOSSARY.md`를 업데이트하세요.
- **사용자가 중요한 근거를 들어 후보를 거절했나요?** 미래의 탐색자가 같은 후보를 다시 추천하지 않으려면 그 근거를 기록해야 할 때에만 _"향후 아키텍처 검토에서 다시 추천하지 않도록 ADR로 기록할까요?"_라고 제안하세요. "지금은 할 가치가 없다"처럼 일시적인 이유나 자명한 이유에는 제안하지 마세요.
- **심화된 모듈의 대안 interface를 살펴보고 싶나요?** Skill 도구로 "codebase-design"을 호출하고 여러 하위 에이전트가 병렬로 설계하는 design-it-twice 패턴을 사용하세요.
