# 리뷰

`HEAD`와 사용자가 제공한 기준점 사이의 diff를 두 축으로 검토:

- **표준** — 코드가 이 저장소의 문서화된 코딩 표준을 따르는가?
- **명세** — 코드가 원본 이슈 / PRD / 명세를 충실히 구현했는가?

두 축 모두 **병렬 하위 에이전트**로 실행되어 서로의 컨텍스트를 오염시키지 않으며, 그 후 이 스킬이 결과를 취합합니다.

이슈 트래커가 제공되어 있어야 합니다 — `docs/agents/issue-tracker.md`가 없으면 `/setup-matt-pocock-skills`를 실행하세요.

## 절차

### 1. 기준점 고정

사용자가 말한 것이 기준점입니다 — 커밋 SHA, 브랜치명, 태그, `main`, `HEAD~5` 등. 의견을 내지 말고 그대로 전달하세요. 지정하지 않았다면 물어보세요: "어디를 기준으로 리뷰할까요 — 브랜치, 커밋, 아니면 `main`?" 기준점을 확보할 때까지 진행하지 마세요.

diff 명령을 한 번 캡처하세요: `git diff <기준점>...HEAD` (점 세 개, merge-base를 기준으로 비교). 또한 `git log <기준점>..HEAD --oneline`으로 커밋 목록도 기록하세요.

### 2. 명세 출처 식별

다음 순서로 원본 명세를 찾으세요:

1. 커밋 메시지의 이슈 참조 (`#123`, `Closes #45`, GitLab `!67` 등) — `docs/agents/issue-tracker.md`의 워크플로우를 통해 가져오세요.
2. 사용자가 인자로 전달한 경로.
3. `docs/`, `specs/`, `.scratch/` 아래에 브랜치명이나 기능명과 일치하는 PRD/명세 파일.
4. 아무것도 찾지 못하면 사용자에게 명세 위치를 물어보세요. 없다고 하면 **명세** 하위 에이전트는 건너뛰고 "명세 없음"으로 보고합니다.

### 3. 표준 출처 식별

코드 작성 방식을 문서화한 저장소 내 모든 것. 일반적인 위치:

- `CLAUDE.md`, `AGENTS.md`
- `CONTRIBUTING.md`
- `CONTEXT.md`, `CONTEXT-MAP.md`, 컨텍스트별 `CONTEXT.md` 파일
- `docs/adr/` (아키텍처 결정은 표준임)
- `.editorconfig`, `eslint.config.*`, `biome.json`, `prettier.config.*`, `tsconfig.json` (도구가 강제하는 표준 — 기록은 하되 도구가 이미 검사하는 것은 재검사하지 말 것)
- 저장소 루트나 `docs/` 아래의 `STYLE.md`, `STANDARDS.md`, `STYLEGUIDE.md` 또는 유사 파일

파일 목록을 수집하세요. **표준** 하위 에이전트가 이를 읽을 것입니다.

### 4. 두 하위 에이전트를 병렬로 실행

하나의 메시지에 두 개의 `Agent` 도구 호출을 보내세요. 둘 다 `general-purpose` 하위 에이전트를 사용하세요.

**표준 하위 에이전트 프롬프트** — 포함할 내용:

- 전체 diff 명령과 커밋 목록.
- 3단계에서 찾은 표준 출처 파일 목록.
- 브리핑: "표준 문서를 읽으세요. 그 다음 diff를 읽으세요. diff가 문서화된 표준을 위반한 모든 지점을 파일/헝크별로 보고하세요. 표준을 인용하세요(파일 + 규칙). 명백한 위반과 판단이 필요한 부분을 구분하세요. 도구가 강제하는 것은 건너뛰세요. 400단어 이내."

**명세 하위 에이전트 프롬프트** — 포함할 내용:

- diff 명령과 커밋 목록.
- 명세의 경로 또는 가져온 내용.
- 브리핑: "명세를 읽으세요. 그 다음 diff를 읽으세요. 보고할 내용: (a) 명세가 요청했지만 누락되거나 부분적인 요구사항; (b) 요청되지 않은 diff 내 동작 (범위 확장); (c) 구현된 것처럼 보이지만 구현이 잘못된 요구사항. 각 발견 사항에 대해 명세 줄을 인용하세요. 400단어 이내."

명세가 없으면 명세 하위 에이전트를 건너뛰고 최종 보고서에 이를 명시하세요.

### 5. 취합

두 보고서를 `## 표준`과 `## 명세` 제목 아래에 그대로 또는 가볍게 정리하여 제시하세요. 결과를 **병합하거나 재순위화하지 마세요** — 두 축은 사용자가 독립적으로 볼 수 있도록 의도적으로 분리되어 있습니다.

축별 총 발견 수와 가장 심각한 단일 이슈(있는 경우)를 한 줄로 요약하여 마무리하세요.

## 두 축이 필요한 이유

변경사항이 한 축은 통과하고 다른 축은 실패할 수 있습니다:

- 모든 표준을 따르지만 잘못된 것을 구현한 코드 → **표준 통과, 명세 실패.**
- 이슈가 요청한 것을 정확히 수행하지만 프로젝트의 관례를 깨는 코드 → **명세 통과, 표준 실패.**

별도로 보고함으로써 한 축이 다른 축을 가리는 것을 방지합니다.
