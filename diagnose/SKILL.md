# 진단

어려운 버그를 위한 규율. 명시적으로 정당화된 경우에만 단계를 건너뛰세요.

코드베이스를 탐색할 때는 프로젝트의 도메인 용어집을 사용하여 관련 모듈에 대한 명확한 멘탈 모델을 얻고, 다루는 영역의 ADR을 확인하세요.

## 1단계 — 피드백 루프 구축

**이것이 핵심 기술입니다.** 나머지는 기계적인 작업입니다. 버그에 대한 빠르고, 결정적이며, 에이전트가 실행 가능한 합격/불합격 신호가 있다면 원인을 찾을 수 있습니다 — 이분 탐색, 가설 검증, 계측 모두 그 신호를 소비할 뿐입니다. 신호가 없으면 아무리 코드를 들여다봐도 소용없습니다.

여기에 불균형적으로 많은 노력을 쏟으세요. **공격적으로, 창의적으로. 포기하지 마세요.**

### 피드백 루프 구축 방법 — 대략 이 순서대로 시도하세요

1. **실패하는 테스트** — 버그에 도달하는 임의의 이음새에서: 유닛, 통합, e2e.
2. **Curl / HTTP 스크립트** — 실행 중인 개발 서버에 대해.
3. **CLI 호출** — 픽스처 입력으로, stdout을 알려진 양호한 스냅샷과 diff.
4. **헤드리스 브라우저 스크립트** (Playwright / Puppeteer) — UI를 구동하고 DOM/콘솔/네트워크에서 검증.
5. **캡처된 트레이스 재생.** 실제 네트워크 요청 / 페이로드 / 이벤트 로그를 디스크에 저장하고; 격리된 상태에서 코드 경로를 통해 재생.
6. **임시 하네스.** 단일 함수 호출로 버그 코드 경로를 실행하는 시스템의 최소 하위 집합(서비스 하나, 모의 의존성)을 구동.
7. **속성 / 퍼즈 루프.** 버그가 "가끔 잘못된 출력"인 경우, 무작위 입력 1000개를 실행하여 실패 모드를 찾기.
8. **이분 탐색 하네스.** 두 알려진 상태(커밋, 데이터셋, 버전) 사이에서 버그가 나타났다면, `git bisect run`으로 실행할 수 있도록 "상태 X에서 부팅, 확인, 반복"을 자동화.
9. **차등 루프.** 동일한 입력을 구버전 vs 신버전(또는 두 설정)으로 실행하고 출력을 diff.
10. **HITL bash 스크립트.** 최후의 수단. 사람이 클릭해야 한다면, `scripts/hitl-loop.template.sh`로 그들을 구동하여 루프가 여전히 구조화되게 하기. 캡처된 출력이 피드백으로 돌아옴.

올바른 피드백 루프를 구축하면, 버그는 90% 해결된 것입니다.

### 루프 자체를 개선하세요

루프를 제품처럼 다루세요. 일단 _어떤_ 루프가 생기면, 자문하세요:

- 더 빠르게 만들 수 있나? (설정 캐시, 관련 없는 초기화 건너뛰기, 테스트 범위 좁히기)
- 신호를 더 날카롭게 만들 수 있나? ("충돌하지 않았다"가 아니라 특정 증상으로 검증)
- 더 결정적으로 만들 수 있나? (시간 고정, RNG 시드, 파일 시스템 격리, 네트워크 동결)

30초짜리 불안정한 루프는 루프가 없는 것보다 겨우 나을 뿐입니다. 2초짜리 결정적 루프는 디버깅 초능력입니다.

### 비결정적 버그

목표는 깔끔한 재현이 아니라 **더 높은 재현율**입니다. 트리거를 100회 반복, 병렬화, 스트레스 추가, 타이밍 윈도우 좁히기, sleep 주입. 50% 재현율의 버그는 디버깅 가능합니다; 1%는 불가능 — 디버깅 가능해질 때까지 재현율을 계속 올리세요.

### 정말로 루프를 구축할 수 없는 경우

멈추고 명시적으로 말하세요. 시도한 것을 나열하세요. 사용자에게 요청: (a) 버그를 재현하는 환경에 대한 접근, (b) 캡처된 아티팩트(HAR 파일, 로그 덤프, 코어 덤프, 타임스탬프가 있는 화면 녹화), (c) 임시 프로덕션 계측 추가 권한. 루프 없이 **절대** 가설 단계로 진행하지 마세요.

믿을 수 있는 루프가 생길 때까지 2단계로 진행하지 마세요.

## 2단계 — 재현

루프를 실행하세요. 버그가 나타나는 것을 지켜보세요.

확인:

- [ ] 루프가 **사용자**가 설명한 실패 모드를 생성함 — 우연히 근처에 있는 다른 실패가 아님. 잘못된 버그 = 잘못된 수정.
- [ ] 여러 실행에 걸쳐 재현 가능함 (또는 비결정적 버그의 경우, 디버깅할 수 있을 만큼 높은 비율로 재현 가능).
- [ ] 정확한 증상(오류 메시지, 잘못된 출력, 느린 타이밍)을 캡처하여 이후 단계에서 수정이 실제로 해결했는지 검증할 수 있음.

버그를 재현할 때까지 진행하지 마세요.

## 3단계 — 가설 수립

테스트하기 전에 **3-5개의 순위가 매겨진 가설**을 생성하세요. 단일 가설 생성은 첫 번째 그럴듯한 아이디어에 고정됩니다.

각 가설은 **반증 가능**해야 합니다: 예측을 명시하세요.

> 형식: "만약 <X>가 원인이라면, <Y를 변경하면> 버그가 사라질 것이다 / <Z를 변경하면> 악화될 것이다."

예측을 명시할 수 없다면, 그 가설은 느낌일 뿐입니다 — 버리거나 날카롭게 다듬으세요.

**테스트하기 전에 순위가 매겨진 목록을 사용자에게 보여주세요.** 사용자는 종종 순위를 즉시 재조정할 도메인 지식이 있거나("#3에 방금 변경을 배포했어"), 이미 제외한 가설을 알고 있습니다. 저렴한 체크포인트, 큰 시간 절약. 기다리느라 멈추지 마세요 — 사용자가 AFK 상태면 당신의 순위대로 진행하세요.

## 4단계 — 계측

각 프로브는 3단계의 특정 예측에 매핑되어야 합니다. **한 번에 하나의 변수만 변경하세요.**

도구 선호도:

1. **디버거 / REPL 검사** — 환경이 지원한다면. 중단점 하나가 로그 열 개보다 낫습니다.
2. **대상화된 로그** — 가설을 구분하는 경계에서.
3. 절대 "모든 것 로깅하고 grep" 하지 마세요.

**모든 디버그 로그에** 고유 접두사 태그, 예: `[DEBUG-a4f2]`. 마지막 정리 시 단일 grep으로 가능. 태그 없는 로그는 살아남고; 태그 있는 로그는 사라집니다.

**성능 브랜치.** 성능 저하의 경우, 로그는 보통 틀린 방법입니다. 대신: 기준 측정 수립(타이밍 하네스, `performance.now()`, 프로파일러, 쿼리 플랜), 그 다음 이분 탐색. 측정 먼저, 수정은 그 다음.

## 5단계 — 수정 + 회귀 테스트

**수정 전에 회귀 테스트를 작성하세요** — 하지만 올바른 이음새가 있는 경우에만.

올바른 이음새는 테스트가 호출 지점에서 발생하는 **실제 버그 패턴**을 실행하는 것입니다. 사용 가능한 유일한 이음새가 너무 얕다면(버그가 여러 호출자를 필요로 하는데 단일 호출자 테스트, 버그를 트리거한 체인을 복제할 수 없는 유닛 테스트), 그곳의 회귀 테스트는 거짓 확신을 줍니다.

**올바른 이음새가 존재하지 않는다면, 그 자체가 발견입니다.** 기록하세요. 코드베이스 아키텍처가 버그를 잠그지 못하게 하고 있습니다. 다음 단계를 위해 플래그를 세우세요.

올바른 이음새가 존재한다면:

1. 최소화된 재현을 해당 이음새에서 실패하는 테스트로 전환.
2. 실패하는지 확인.
3. 수정 적용.
4. 통과하는지 확인.
5. 원래(최소화되지 않은) 시나리오에 대해 1단계 피드백 루프 재실행.

## 6단계 — 정리 + 사후 분석

완료 선언 전 필수 사항:

- [ ] 원래 재현이 더 이상 재현되지 않음 (1단계 루프 재실행)
- [ ] 회귀 테스트 통과 (또는 이음새 부재가 문서화됨)
- [ ] 모든 `[DEBUG-...]` 계측 제거됨 (접두사로 `grep`)
- [ ] 임시 프로토타입 삭제됨 (또는 명확히 표시된 디버그 위치로 이동)
- [ ] 올바른 것으로 판명된 가설이 커밋 / PR 메시지에 명시됨 — 다음 디버거가 배울 수 있도록

**그런 다음 자문하세요: 무엇이 이 버그를 예방할 수 있었을까?** 답이 아키텍처 변경(좋은 테스트 이음새 없음, 얽힌 호출자, 숨겨진 결합)을 포함한다면, 구체적 내용과 함께 `/improve-codebase-architecture` 스킬로 넘기세요. 수정이 완료된 **후에** 권장사항을 만들고, 그 전에는 하지 마세요 — 시작했을 때보다 지금이 더 많은 정보를 가지고 있습니다.
