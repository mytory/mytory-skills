# 도메인 모델링

설계하는 동안 프로젝트의 도메인 모델을 적극적으로 만들고 다듬습니다. 용어에 이의를 제기하고, 경계 사례를 만들고, 용어와 결정이 명확해지는 즉시 기록하는 *능동적인* 작업입니다. (`GLOSSARY.md`에서 용어를 *읽기만* 하는 일은 이 스킬이 아닙니다. 이는 어느 스킬에서나 할 수 있는 간단한 습관입니다. 이 스킬은 모델을 바꿀 때 사용합니다.)

## 파일 구조

대부분의 저장소에는 컨텍스트가 하나 있습니다.

```
/
├── GLOSSARY.md
├── docs/
│   └── adr/
│       ├── 0001-event-sourced-orders.md
│       └── 0002-postgres-for-write-model.md
└── src/
```

루트에 `GLOSSARY-MAP.md`가 있으면 여러 컨텍스트가 있는 저장소입니다. 이 파일은 각 컨텍스트의 위치를 가리킵니다.

```
/
├── GLOSSARY-MAP.md
├── docs/
│   └── adr/                          ← 시스템 전체에 적용되는 결정
├── src/
│   ├── ordering/
│   │   ├── GLOSSARY.md
│   │   └── docs/adr/                 ← 해당 컨텍스트에 적용되는 결정
│   └── billing/
│       ├── GLOSSARY.md
│       └── docs/adr/
```

파일은 기록할 내용이 생겼을 때 만듭니다. `GLOSSARY.md`가 없다면 첫 용어가 확정될 때 만듭니다. `docs/adr/`가 없다면 첫 ADR이 필요할 때 만듭니다.

## 세션 중에 할 일

### 용어집과 대조하기

사용자의 용어가 기존 `GLOSSARY.md`의 언어와 충돌하면 즉시 알립니다. "용어집에서는 '취소'를 X로 정의했는데, 지금 말씀하신 것은 Y로 보입니다. 어느 쪽인가요?"

### 모호한 언어 다듬기

사용자가 모호하거나 여러 의미로 쓰이는 용어를 사용하면 정확한 표준 용어를 제안합니다. "'계정'이라고 하셨는데 고객과 사용자 중 어느 쪽인가요? 둘은 다른 개념입니다."

### 구체적인 시나리오 논의하기

도메인 관계를 논의할 때는 구체적인 상황으로 검증합니다. 경계 사례를 드러내고 개념 간 경계를 정확하게 정의하도록 만드는 시나리오를 구성합니다.

### 코드와 교차 확인하기

사용자가 어떤 동작을 설명하면 코드와 일치하는지 확인합니다. 모순을 발견하면 드러냅니다. "코드에서는 주문 전체를 취소하는데, 방금 부분 취소가 가능하다고 하셨습니다. 어느 쪽이 맞나요?"

### GLOSSARY.md를 즉시 갱신하기

용어가 확정되면 그 자리에서 `GLOSSARY.md`를 갱신합니다. 나중에 한꺼번에 처리하지 말고 결정될 때마다 기록합니다. [GLOSSARY-FORMAT.md](./GLOSSARY-FORMAT.md)의 형식을 따릅니다.

`GLOSSARY.md`에는 구현 세부 사항을 넣지 않습니다. 이를 명세서, 메모장 또는 구현 결정의 기록 장소로 쓰지 않습니다. 오직 용어집으로 사용합니다.

### ADR은 신중하게 제안하기

다음 세 조건을 모두 만족할 때만 ADR 작성을 제안합니다.

1. **되돌리기 어렵다**: 나중에 결정을 바꾸는 비용이 상당하다.
2. **맥락 없이는 의아하다**: 미래의 독자가 "왜 이렇게 했을까?"라고 생각할 만하다.
3. **실질적인 득실 판단의 결과다**: 실제 대안이 있었고 구체적인 이유로 하나를 선택했다.

하나라도 해당하지 않으면 ADR을 생략합니다. [ADR-FORMAT.md](./ADR-FORMAT.md)의 형식을 따릅니다.
