# 보편 언어

현재 대화에서 도메인 용어를 추출하고 공식화하여 일관된 용어집으로 만들고 로컬 파일로 저장하세요.

## 절차

1. **대화 스캔** — 도메인 관련 명사, 동사, 개념 찾기
2. **문제 식별**:
   - 같은 단어가 다른 개념에 사용됨 (모호성)
   - 다른 단어가 같은 개념에 사용됨 (동의어)
   - 모호하거나 과부하된 용어
3. **공식 용어집 제안** — 주관적인 용어 선택
4. **`UBIQUITOUS_LANGUAGE.md`에 작성** — 아래 형식을 사용해 작업 디렉터리에 저장
5. **요약 출력** — 대화에 인라인으로

## 출력 형식

다음 구조로 `UBIQUITOUS_LANGUAGE.md` 파일 작성:

```md
# 보편 언어

## 주문 생명주기

| 용어            | 정의                                           | 피해야 할 별칭          |
| --------------- | ---------------------------------------------- | ----------------------- |
| **Order**       | 하나 이상의 상품을 구매하기 위한 고객의 요청    | Purchase, transaction   |
| **Invoice**     | 배송 후 고객에게 발송되는 지불 요청             | Bill, payment request   |

## 사람

| 용어             | 정의                                     | 피해야 할 별칭            |
| ---------------- | ---------------------------------------- | ------------------------- |
| **Customer**     | 주문을 하는 사람 또는 조직               | Client, buyer, account    |
| **User**         | 시스템의 인증 주체                       | Login, account            |

## 관계

- **Invoice**는 정확히 하나의 **Customer**에 속함
- **Order**는 하나 이상의 **Invoice**를 생성함

## 예시 대화

> **개발자:** "**Customer**가 **Order**를 하면 바로 **Invoice**를 생성하나요?"
> **도메인 전문가:** "아니요 — **Invoice**는 **Fulfillment**가 확인된 후에만 생성됩니다. 하나의 **Order**가 별도의 **Shipment**로 배송되면 여러 **Invoice**를 생성할 수 있습니다."
> **개발자:** "그러면 **Shipment**가 발송 전에 취소되면 해당 **Invoice**는 존재하지 않나요?"
> **도메인 전문가:** "정확합니다. **Invoice** 생명주기는 **Order**가 아닌 **Fulfillment**에 연결됩니다."

## 지적된 모호성

- "account"가 **Customer**와 **User** 양쪽을 의미하는 데 사용됨 — 이들은 별개의 개념: **Customer**는 주문을 하고, **User**는 **Customer**를 대표할 수도 있고 아닐 수도 있는 인증 주체임.
```

## 규칙

- **주관적이세요.** 같은 개념에 여러 단어가 있으면 가장 좋은 것을 고르고 나머지는 피해야 할 별칭으로 나열.
- **충돌을 명시적으로 지적.** 대화에서 용어가 모호하게 사용되면 "지적된 모호성" 섹션에 명확한 권장사항과 함께 지적.
- **도메인 전문가에게 관련된 용어만 포함.** 모듈이나 클래스 이름은 도메인 언어에서 의미가 없으면 건너뛰기.
- **정의는 간결하게.** 최대 한 문장. 무엇인지 정의하고, 무엇을 하는지 정의하지 않음.
- **관계 보여주기.** 볼드 용어명 사용, 명백한 경우 기수성 표현.
- **도메인 용어만 포함.** 도메인 특정 의미가 없으면 일반 프로그래밍 개념(array, function, endpoint) 건너뛰기.
- **자연스러운 군집이 생기면 여러 테이블로 그룹화** (예: 하위 도메인, 생명주기, 행위자별). 각 그룹은 자체 제목과 테이블을 가짐. 모든 용어가 단일 응집 도메인에 속하면 하나의 테이블로 충분 — 강제로 그룹화하지 않음.
- **예시 대화 작성.** 용어가 어떻게 자연스럽게 상호작용하는지 보여주는 개발자와 도메인 전문가 간의 짧은 대화(3-5회 교환). 대화는 관련 개념 간 경계를 명확히 하고 용어가 정확히 사용되는 모습을 보여줘야 함.

## 예시 대화

> **개발자:** "Docker 없이 **sync service**를 어떻게 테스트하나요?"

> **도메인 전문가:** "**Docker layer** 대신 **filesystem layer**를 제공하세요. 동일한 **Sandbox service** 인터페이스를 구현하지만 로컬 디렉터리를 **sandbox**로 사용합니다."

> **개발자:** "그럼 **sync-in**이 여전히 **bundle**을 만들고 풀어내나요?"

> **도메인 전문가:** "정확합니다. **sync service**는 자신이 어떤 레이어와 통신하는지 모릅니다. `exec`와 `copyIn`을 호출할 뿐 — **filesystem layer**는 그것들을 로컬 셸 명령으로 실행합니다."

</example>

## 재실행

같은 대화에서 다시 호출될 때:

1. 기존 `UBIQUITOUS_LANGUAGE.md` 읽기
2. 후속 논의의 새 용어 통합
3. 이해가 발전했으면 정의 업데이트
4. 새 모호성 다시 지적
5. 새 용어를 통합해 예시 대화 재작성
