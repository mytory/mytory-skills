# 인터페이스 설계

"소프트웨어 설계 철학"의 "두 번 설계하기" 원칙에 기반: 첫 번째 아이디어가 최선일 가능성은 낮습니다. 근본적으로 다른 여러 설계를 생성한 다음 비교하세요.

## 작업 흐름

### 1. 요구사항 수집

설계 전에 이해해야 할 것:

- [ ] 이 모듈이 해결하는 문제는 무엇인가?
- [ ] 호출자는 누구인가? (다른 모듈, 외부 사용자, 테스트)
- [ ] 주요 작업은 무엇인가?
- [ ] 제약 조건이 있는가? (성능, 호환성, 기존 패턴)
- [ ] 내부에 숨길 것과 외부에 노출할 것은 무엇인가?

질문: "이 모듈이 무엇을 해야 하나요? 누가 사용하나요?"

### 2. 설계 생성 (병렬 하위 에이전트)

Task 도구를 사용해 3개 이상의 하위 에이전트를 동시에 실행하세요. 각각 **근본적으로 다른** 접근 방식을 생성해야 합니다.

```
각 하위 에이전트를 위한 프롬프트 템플릿:

[모듈 설명]에 대한 인터페이스를 설계하세요.

요구사항: [수집된 요구사항]

이 설계의 제약 조건: [각 에이전트에 다른 제약 조건 할당]
- 에이전트 1: "메서드 수 최소화 - 최대 1-3개 메서드 목표"
- 에이전트 2: "유연성 극대화 - 많은 사용 사례 지원"
- 에이전트 3: "가장 일반적인 경우에 최적화"
- 에이전트 4: "[특정 패러다임/라이브러리]로부터 영감 얻기"

출력 형식:
1. 인터페이스 시그니처 (타입/메서드)
2. 사용 예시 (호출자가 어떻게 사용하는지)
3. 이 설계가 내부적으로 숨기는 것
4. 이 접근법의 트레이드오프
```

### 3. 설계 제시

각 설계를 다음 요소와 함께 보여주세요:

1. **인터페이스 시그니처** - 타입, 메서드, 매개변수
2. **사용 예시** - 호출자가 실제로 어떻게 사용하는지
3. **숨기는 것** - 내부에 감춰진 복잡성

설계를 순차적으로 제시하여 사용자가 비교 전에 각 접근법을 이해할 수 있게 하세요.

### 4. 설계 비교

모든 설계를 보여준 후 다음 기준으로 비교하세요:

- **인터페이스 단순성**: 적은 메서드, 단순한 매개변수
- **범용성 vs 특수성**: 유연성 vs 집중도
- **구현 효율성**: 인터페이스 형태가 효율적인 내부 구현을 허용하는가?
- **깊이**: 작은 인터페이스가 상당한 복잡성을 숨기는 경우 = 깊은 모듈 (좋음) vs 큰 인터페이스에 얇은 구현 (나쁨)
- **올바른 사용의 용이성** vs **오용의 용이성**

트레이드오프를 표가 아닌 산문으로 논의하세요. 설계가 가장 크게 갈리는 지점을 강조하세요.

### 5. 종합

종종 최상의 설계는 여러 옵션의 통찰을 결합합니다. 물어보세요:

- "어떤 설계가 주요 사용 사례에 가장 잘 맞나요?"
- "다른 설계에서 통합할 가치가 있는 요소가 있나요?"

## 평가 기준

"소프트웨어 설계 철학"에서 발췌:

**인터페이스 단순성**: 적은 메서드, 단순한 매개변수 = 배우기 쉽고 올바르게 사용하기 쉬움.

**범용성**: 변경 없이 미래 사용 사례를 처리할 수 있음. 그러나 과도한 일반화를 주의하세요.

**구현 효율성**: 인터페이스 형태가 효율적인 구현을 허용하는가? 아니면 어색한 내부 구조를 강제하는가?

**깊이**: 작은 인터페이스가 상당한 복잡성을 숨김 = 깊은 모듈 (좋음). 큰 인터페이스에 얇은 구현 = 얕은 모듈 (피해야 함).

## 안티패턴

- 하위 에이전트가 비슷한 설계를 생성하지 않도록 하세요 - 근본적인 차이를 강제하세요
- 비교를 건너뛰지 마세요 - 가치는 대조에 있습니다
- 구현하지 마세요 - 순전히 인터페이스 형태에 관한 것입니다
- 구현 노력으로 평가하지 마세요
